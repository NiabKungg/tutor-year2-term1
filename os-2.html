Operating Systems (ต่อ)

ครึ่งหลังของวิชา: Memory Management, Virtual Memory, File System และการติดตั้ง WSL2 รวมตัวอย่างคำนวณที่อาจารย์ลงลึกในคลิปทุกตัว

Memory Management (No.08 + คลิป 12.1 ถึง 12.4)

หัวข้อนี้ตอบคำถามว่า OS วางโปรแกรมลง RAM อย่างไร ตั้งแต่การแปลง address, การจัดสรรแบบต่อเนื่อง (รุ่นเก่า) ไปจนถึง paging และ segmentation ที่ OS ปัจจุบันใช้

ประเด็นสำคัญ
  • CPU ใช้ logical (virtual) address แต่ RAM ใช้ physical address, ตัวแปลงคือ MMU ด้วย relocation register
  • fixed partition เกิด internal fragmentation, variable partition เกิด external fragmentation
  • Placement: first-fit เร็ว, best-fit ประหยัดสุดแต่ช้า, worst-fit เหลือช่องใหญ่ไว้ใช้ต่อ
  • Paging แก้ปัญหา fragmentation ด้วยการกระจาย page ลง frame, แลกกับการ access memory 2 ครั้ง จึงต้องมี TLB
  • Segmentation จัดตามมุมมองผู้ใช้ ใช้ <segment-number, offset> กับ base/limit

Logical address, Physical address และ MMU

Logical (virtual) address คือ address ที่ CPU generate ออกมา ส่วน physical address คือตำแหน่งจริงที่ memory unit เห็น โปรแกรมไม่ได้ถูกโหลดเริ่มที่ไบต์ 0 ของ RAM แต่ถูก OS จัดสรรไปตามที่ว่าง

ตัวแปลง logical เป็น physical คือฮาร์ดแวร์ที่เรียกว่า MMU (Memory-Management Unit) แบบง่ายใช้ relocation register: ค่าใน register ถูกบวกเข้าทุก address ที่ user process generate และ user program เห็นแต่ logical address เท่านั้น

ตัวอย่าง: แปลง address ด้วย relocation register (คลิป 12.1)
  1. โปรแกรมถูกโหลดลง RAM ที่ address 14,000, ค่านี้เก็บใน relocation register
  2. CPU ต้องการไบต์ที่ 346 (logical address)
  3. MMU บวกเลย: physical = 14,000 + 346 = 14,346

อาจารย์ย้ำว่านี่เป็น concept ง่าย ๆ เพื่อเห็นภาพ ของจริงยุ่งยากกว่านี้

ตอนป้องกัน process แทรกแซงกัน (คลิป 12.2) ใช้ 2 register ช่วยกัน: Limit register เก็บขนาดของพื้นที่, Relocation register เก็บตำแหน่งเริ่มต้น logical address ต้องน้อยกว่า limit ถ้าไม่ใช่ให้ error ทันที ถ้าผ่านจึงบวกกับ relocation register

Static Linking กับ Dynamic Linking

Static link คือเอา library (เช่น printf ของ C) มารวมกับโปรแกรมตอน compile เลย Dynamic linking เลื่อนการ link ไปจนถึง execution time โดยใส่ stub (โค้ดเล็ก ๆ ตัวแทนของ library) เข้าไปแทน หน้าที่ stub คือตอนรันไปค้นว่า library ถูกโหลดเข้า memory หรือยัง ถ้ายังก็โหลดเข้ามา ถ้าโหลดแล้วก็เรียกใช้เลย OS ต้องช่วยตรวจว่า routine อยู่ใน address space ของ process หรือไม่ เพราะเหมาะกับ library จึงเรียกอีกอย่างว่า shared libraries

ตัวอย่าง: static กับ dynamic ประหยัดต่างกันเท่าไร (คลิป 12.1)

โปรแกรม A ตัวเอง 10 MB, โปรแกรม B ตัวเอง 20 MB, library กลาง 20 MB, stub ตัวละ 2 MB

  1. Static: A = 10 + 20 = 30 MB, B = 20 + 20 = 40 MB, รวม 70 MB โดยมี library 20 MB ถูกเก็บซ้ำ 2 ที่
  2. Dynamic: A = 10 + 2 (stub) = 12 MB, B = 20 + 2 = 22 MB
  3. รัน A ก่อน (12 MB), A เรียก library ผ่าน stub, stub พบว่ายังไม่ถูกโหลด จึงโหลด library 20 MB (รวม 32 MB)
  4. รัน B (22 MB), B เรียก library ผ่าน stub พบว่าโหลดแล้ว ใช้ร่วมกับ A ไม่โหลดซ้ำ
  5. รวมทั้งหมด = 12 + 20 + 22 = 54 MB เทียบกับ 70 MB ของ static จึงประหยัด memory

การจัดสรรแบบต่อเนื่อง: Fixed และ Variable Partition

การจัดสรรให้ process แบ่งเป็น contiguous (โหลดลงพื้นที่ติดกันเป็นผืนเดียว) กับ non-contiguous (แบ่งเป็นส่วน ๆ วางช่องว่างที่ไม่ติดกันได้) อาจารย์บอกตรง ๆ ว่าแบบ contiguous ตกยุคแล้ว OS ปัจจุบันไม่ใช้ แต่เรียนเพื่อรู้ว่ามันมีปัญหาอะไร และเป็นรากของทั้ง internal และ external fragmentation

Fixed partition: แบ่ง memory เป็น partition ขนาดคงที่ล่วงหน้า เปิดเครื่องแล้วใช้ตลอด จะเปลี่ยนต้องปิดเครื่องมา config ใหม่ Memory Manager ใช้ตารางติดตามว่า partition ไหนว่าง ถ้าแบ่ง 3 partitions ก็รันได้สูงสุด 3 processes พร้อมกัน วิธีจัดคิวแบบแรกคือทำ job queue ต่อ partition (job เล็กไม่เกิน P1 เข้าคิว 1 ฯลฯ) ปัญหาคือถ้ามีแต่ job ตัวเล็ก memory ส่วนใหญ่ว่างเปล่า จึงแก้ด้วยการรวมเหลือ คิวเดียว แล้วจัดสรร job ลง partition ว่างที่ลงได้

ปัญหาของ fixed partition คือ Internal fragmentation: เนื้อที่เหลือใน partition ที่ process ใช้ไม่หมด คนอื่นใช้ต่อไม่ได้ เช่น partition 5 MB แต่ process ใช้ 4 MB เหลือ 1 MB สูญเปล่า

ตัวอย่าง: internal fragmentation ของ fixed partition (คลิป 12.2)

memory แบ่ง 4 partitions: P1 = 100K, P2 = 25K, P3 = 25K, P4 = 50K

  1. Job1 30K ลง P1 (ใช้ 30K เหลือว่างใน partition นั้น 70K)
  2. Job2 50K ลง P4 พอดีตัว
  3. Job3 30K เหลือแต่ P2, P3 ที่มีแค่ 25K จึงลงไม่ได้ ต้องรอ
  4. Job4 25K ลง P2 ได้พอดี

สรุป: P1 ยังว่างอยู่ถึง 70K แต่ Job3 ที่ต้องการแค่ 30K กลับโหลดไม่ได้ นี่คือตำหนิของ fixed partition

Variable partition: ไม่แบ่งล่วงหน้า จัดสรรตอนโหลดตามที่ process ขอ เช่น ขอ 15 MB ได้ 15 MB ตอนตั้งต้นไม่เสียเนื้อที่เลย (internal fragmentation เป็นไปไม่ได้) แต่พอ process จบและถอดออกไป เกิด External fragmentation: ช่องว่างกระจัดกระจาย รวมกันได้เยอะแต่ช่องเดียวไม่พอ

ตัวอย่าง: external fragmentation (คลิป 12.2)
  1. process เก่าจบไปเหลือช่องว่าง 5 MB, 2 MB และ 1 MB กระจายกัน รวม 8 MB
  2. process ใหม่ต้องการ 7 MB ซึ่งน้อยกว่า 8 MB รวม
  3. แต่ contiguous ต้องได้เนื้อที่ต่อเนื่องผืนเดียว ไม่มีช่องไหนพอ จึงโหลดเข้าไม่ได้

วิธีรับมือ external fragmentation มี 2 ทาง:

  • Coalescing: รวม free block ที่อยู่ติดกันเป็นก้อนใหญ่ (ข้อจำกัด: รวมได้เฉพาะช่องที่ติดกันเท่านั้น มักไม่พอใช้)
  • Compaction (garbage collection ของ memory): ย้าย process ที่รันอยู่ให้มาอยู่ติดกันเป็นผืนเดียว เหลือ free block ใหญ่ก้อนเดียวท้าย memory แต่ overhead สูง ต้องหยุด process และทำได้เฉพาะเมื่อ relocation เป็นแบบ dynamic ที่กำหนด address ใหม่ตอน execution time ได้

Placement: First Fit, Best Fit, Worst Fit

เมื่อ process ใหม่มาขอพื้นที่แล้วมีหลาย hole ต้องเลือกว่าจะใส่ hole ไหน

อัลกอริทึมเลือก hole แบบไหนข้อดีข้อเสีย
First-fithole แรกที่พอ จากต้นไปหาท้ายเร็ว, overhead ต่ำเปลือง memory ได้ เพราะไม่สนประสิทธิภาพการใช้พื้นที่
Best-fithole ที่เหลือน้อยสุด (ต้องไล่ดูทุกช่อง)ใช้พื้นที่คุ้มสุดช้า เพราะต้องค้นทุกช่อง
Worst-fithole ที่เหลือมากสุดเหลือช่องใหญ่ไว้ให้ process อื่นใช้ต่อโดยเฉลี่ยประสิทธิภาพสู้ best-fit ไม่ได้
ตัวอย่าง: ช่องว่าง 16, 14, 5, 30 MB กับ process ใหม่ 13 MB (คลิป 12.2)
  1. First-fit: ไล่จากต้น เจอช่องแรกที่ลงได้คือ 16 MB, ใส่เลย เหลือว่าง 16 - 13 = 3 MB (ทั้งที่ถ้าลงช่อง 14 MB จะเหลือแค่ 1 MB แต่ first-fit ไม่สน)
  2. Best-fit: ดูทุกช่อง (16, 14, 5, 30) ช่องที่เหมาะที่สุดกับ 13 MB คือ 14 MB, ใส่แล้วเหลือ 1 MB
  3. Worst-fit: เลือกช่องใหญ่สุดคือ 30 MB, ใส่แล้วเหลือ 17 MB ซึ่งยังใหญ่พอให้ process อื่นใช้ต่อ

อาจารย์เสริมว่าถ้ามี process ใหญ่มาถึง worst-fit อาจดีกว่า best-fit เพราะ best-fit มักเหลือแต่ช่องเล็ก ๆ ที่ใช้ต่อไม่ได้

Paging: การจองแบบไม่ต่อเนื่อง

รากของปัญหา fragmentation ทั้งสองแบบคือการจัดสรรแบบ contiguous ทางออกคือ non-contiguous ซึ่งก็คือ paging ที่ OS ปัจจุบันใช้ วิธีคือแบ่ง physical memory เป็นบล็อกขนาดเท่ากันเรียกว่า frame (ขนาดต้องเป็น power of 2, สไลด์ระบุช่วง 512 ถึง 8,192 bytes) แบ่ง logical memory เป็นบล็อกขนาดเท่ากันเรียกว่า page โปรแกรม n pages ใช้ frame ว่าง n อัน แต่ไม่จำเป็นต้องอยู่ติดกัน OS โหลด page ไหนลง frame ไหนก็ได้ แล้วตั้ง page table เป็นตัวจับคู่แปลง logical เป็น physical

ข้อแลกเปลี่ยน: paging ยังเกิด internal fragmentation ได้ที่ page สุดท้ายของโปรแกรม

ตัวอย่าง: internal fragmentation ใน paging (คลิป 12.3.1)
  1. page/frame size = 4 bytes, โปรแกรมขนาด 42 bytes
  2. ถ้าตอบ 10 เพจจะได้แค่ 40 bytes ไม่พอ
  3. ต้องใช้ 11 เพจ โดยเพจสุดท้ายใช้จริงแค่ 2 จาก 4 bytes เหลือ 2 bytes เป็น internal fragmentation

แบ่ง address เป็น page number กับ page offset

address ยาว m bits ถูกแบ่งเป็น 2 ส่วน: page number (p) ใช้เป็น index เข้า page table หา frame, กับ page offset (d) บอกตำแหน่งในหน้า จำนวนบิต offset คือ n โดยที่ page size = 2^n (เช่น page 4 bytes ต้องใช้ n = 2, page 8 bytes ใช้ n = 3) และ page number เหลือ m - n bits

ตัวอย่าง: m = 5 bits, page size 4 bytes (สไลด์ + คลิป 12.3.1)
  1. address space = 2^5 = 32 bytes, offset n = 2 bits (2^2 = 4)
  2. page number = 5 - 2 = 3 bits จึงมีได้ 2^3 = 8 เพจ เพจละ 4 bytes (8 x 4 = 32 พอดี)
  3. วิธีอ้างเปลี่ยนจาก "ไบต์ที่ 0, 1, 2, 3 ไปตรง ๆ" เป็น "เพจที่เท่าไร + offset ที่เท่าไร"
  4. อุปมาของอาจารย์: เก้าอี้ 32 ตัว จัดเป็น 8 ห้อง ห้องละ 4 ตัว ของก็บอกว่า "เก้าอี้ตัวที่ 3 ในห้องเบอร์ 1"
ตัวอย่าง: แปลง logical เป็น physical, physical = (frame x page size) + offset (คลิป 12.3.1)
  1. ต้องการตัวอักษร C ซึ่งอยู่ page 0, offset 2: ค้น page table พบ page 0 อยู่ frame 5, physical = 5 x 4 + 2 = ไบต์ที่ 22
  2. ต้องการตัวอักษร K ซึ่งอยู่ page 2, offset 2: ค้น page table พบ page 2 อยู่ frame 1, physical = 1 x 4 + 2 = ไบต์ที่ 6
  3. เมื่อมี process ใหม่ 4 เพจเข้ามา OS หา frame ว่างแล้วอัปเดต page table เช่น page 0 ไป frame 14, page 1 ไป frame 13, page 2 ไป frame 18, page 3 ไป frame 20

หมายเหตุ: ภาพรวมในสไลด์หนึ่งแสดงเพจ 0 ถึง 3 โหลดลง frame 1, 4, 3, 7 ตามลำดับ ส่วนตัวอย่างคำนวณในคลิปใช้ page table อีกชุด (page 0 อยู่ frame 5) วิธีคิดเหมือนกันทั้งสองแบบ ให้ดูตาม page table ที่โจทย์กำหนดเสมอ

Page Table อยู่ใน RAM: PTBR, PTLR, TLB และ EAT

Page table เก็บใน main memory (RAM) OS ต้องกันเนื้อที่ไว้ให้ มี register คู่: PTBR (page-table base register) ชี้ตำแหน่งเริ่มต้นของตาราง, PTLR (page-table length register) บอกความยาวของตาราง ใช้เช็คก่อนได้เลยว่าการอ้างเกินหรือไม่ ถ้าเกินไม่ต้องเข้าถึงตารางเลย

ผลคือทุกครั้งที่อ่าน data/instruction 1 ครั้ง ต้องเข้าถึง memory 2 ครั้ง: ครั้งแรกอ่าน page table เพื่อรู้ว่าเพจอยู่ frame ไหน, ครั้งที่สองไปที่ address จริง อาจารย์ย้ำหลายรอบว่านี่คือต้นเหตุที่ต้องมี TLB (translation look-aside buffer) ซึ่งเป็น hardware แบบ associative memory ค้นทุกช่องพร้อมกันได้ในครั้งเดียว

  • TLB hit: ค้นเจอ frame ใน TLB เอาไปคำนวณกับ offset ได้เลย เร็วมากเพราะไม่ต้องเข้าถึง memory
  • TLB miss: ไปค้น page table จริงตามวิธีเดิม แล้วอัปเดต TLB (เต็มเมื่อไรต้องแทนที่รายการเก่า)
  • TLB เก็บได้แค่บางส่วนของ page table เพราะเป็น memory เล็ก ๆ ทำใหญ่เท่า RAM ไม่ได้

Effective Access Time (EAT): ให้ memory cycle = 1 ไมโครวินาที, TLB lookup = ε, hit ratio = α สูตรตามสไลด์คือ EAT = (1 + ε)α + (2 + ε)(1 - α) = 2 + ε - α

ตัวอย่าง: คำนวณ EAT = 1.3 ไมโครวินาที (คลิป 12.3.1)
  1. กำหนด: memory access = 1 ไมโครวินาที, TLB access ε = 0.1 ไมโครวินาที, hit ratio α = 0.8 (80%)
  2. แทนสูตร: EAT = 2 + ε - α = 2 + 0.1 - 0.8 = 1.3 ไมโครวินาที
  3. เทียบกับกรณีไม่มี TLB ที่ต้อง access 2 ครั้ง = 2 ไมโครวินาที จึงเร็วขึ้น
  4. วิธีทำให้ EAT ดีขึ้น: ลด ε (TLB เร็วขึ้น) และเพิ่ม α (hit ratio สูงขึ้น)

Memory Protection และ Shared Pages

แต่ละ entry ของ page table มี protection bit กับ valid/invalid bit: valid = page อยู่ใน logical address space ของ process, invalid = ไม่อยู่ เช่น OS สร้างตาราง 8 ช่องให้โปรแกรมใหญ่สุด แต่โปรแกรมใช้จริง 6 เพจ (0 ถึง 5) ก็เซต valid ถึงเพจ 5 ที่เหลือ invalid ถ้า process อ้างเพจ 6 จะ error ทันที

ข้อจำกัดที่อาจารย์ชี้: valid/invalid bit ยังป้องกันไม่หมด เพราะถ้าเพจสุดท้ายใช้ไม่เต็ม (internal fragmentation) process อ้าง offset เกินที่โปรแกรมใช้จริงได้ทั้งเพจ และ valid/invalid bit จะเห็นประโยชน์จริง ๆ ตอนเรื่อง Virtual Memory

Shared pages: paging ทำให้แชร์เพจกันง่าย เช่น editor รัน 3 processes ส่วน code ที่ไม่มีการเปลี่ยนแปลงโหลดลง frame เดียวกันใช้ร่วมกันได้ (เพจ 0, 1, 2 ของทั้ง 3 process ชี้ไปที่ frame 3, 4, 6 หมด) ส่วน data แยกกันคนละ frame หลักการคือ "อะไรที่แน่ใจว่าไม่เปลี่ยนแปลง ใช้ร่วมกันได้"

ทำไมตารางถึงใหญ่: OS 32 บิต, page size 4 KB = 12 bits (offset) เหลือ page number 20 bits จึงมีได้สูงสุด 2^20 = 1 ล้าน entry, 1 entry ขนาด 4 bytes รวมเป็น 4 MB ต่อ process ปัญหาคือโปรแกรมปกติไม่ใหญ่ถึง 4 GB เช่นโปรแกรม 1 MB แต่ต้องสร้าง page table 4 MB ใหญ่กว่าตัวโปรแกรมเสียอีก (เทียบ: OS 64 บิตอ้างได้ถึง 2^64 ประมาณ 18.4 exabyte แต่ของจริงถูกจำกัดที่ประมาณ 48 bits คือราว 256 TB)

ทางแก้มี 3 แบบตามสไลด์: Hierarchical (multilevel), Hashed, Inverted วิชานี้ลงลึกที่ hierarchical คือแบ่ง page table เป็นชั้น ๆ ชั้นนอกชี้ไปชั้นใน ชั้นในสุดเก็บเลข frame จุดสำคัญคือ Level 2 สร้างขึ้นเมื่อจำเป็นเท่านั้น ช่องไหนไม่ใช้ก็ไม่ต้องสร้างตารางให้ นี่คือที่มาของความประหยัด (ถ้านับจำนวนช่องรวมกันแล้วมันไม่ได้ประหยัดเลย)

ตัวอย่าง: two-level paging บน OS 32 บิต, page 4 KB (คลิป 12.3.2)

page number 20 bits แบ่งเป็น outer 10 + inner 10 bits, แต่ละตารางมี 2^10 = 1024 ช่อง (ตารางละ 4 KB)

  1. โปรแกรม 1 MB: จำนวนเพจ = 1024 K / 4 K = 256 เพจ ใช้ตาราง Level 2 แค่ 1 ตาราง (ใช้ 256 จาก 1024 ช่อง)
  2. page table ที่ใช้ = 4 KB (Level 1) + 4 KB (Level 2) = 8 KB เทียบกับ 4 MB ของ single-level
  3. โปรแกรม 8 MB: 8 x 1024 K / 4 K = 2048 เพจ ต้องใช้ตาราง Level 2 2 ตาราง (ใช้เต็ม 0 ถึง 1023 ทั้งคู่), Level 1 ใช้แค่ 2 ช่องแต่ยังต้องสร้างทั้งตาราง
  4. page table ที่ใช้ = 4 KB + 2 x 4 KB = 12 KB สำหรับโปรแกรมขนาดเดียวกัน
  5. การอ้างแบบ 2 ระดับ: (ตารางที่ 0, ช่องที่ 200, offset 500) outer ชี้เข้าตาราง Level 2 ที่ 0, หาช่องที่ 200 ได้เลข frame แล้วนำไปรวมกับ offset

ข้อจำกัด: 2 ระดับไม่พอสำหรับ address space ใหญ่ (64 บิตต้อง 3 ถึง 4 ระดับ) แต่ยิ่งหลายระดับยิ่งช้าเพราะต้อง access ทีละชั้น space ใหญ่มากจึงไปใช้ hashed หรือ inverted page table เหมาะกว่า

Segmentation

Paging ไม่สอดคล้องกับมุมมองผู้ใช้ เพราะเราไม่เคยคิดว่า "จะแบ่งโปรแกรมเป็นกี่เพจ" แต่มองโปรแกรมเป็น main program, procedure, function, method, object, stack, symbol table, array, global variables Segmentation จึงจัด memory ตามมุมมองนี้ เช่น code segment กับ data segment โดยแต่ละ segment ขนาดไม่เท่ากัน กฎคือ segment เดียวต้องได้เนื้อที่ติดกัน (กระจายไม่ได้) แต่คนละ segment กระจายกันได้

  • Logical address = <segment-number, offset>
  • Segment table แต่ละ entry มี base (physical address เริ่มต้น) และ limit (ความยาว segment)
  • STBR ชี้ตำแหน่งเริ่มต้นของ segment table, STLR บอก segment สูงสุดที่อ้างได้ segment number s ถูกต้องเมื่อ s < STLR
  • ขั้นตอนแปลง: ค้น segment table เอา limit กับ base, เช็ค offset < limit ถ้าไม่ผ่านเกิด trap/error, ถ้าผ่าน physical = base + offset
ตัวอย่าง: แปลง address แบบ segmentation (คลิป 12.4)

Segment table: segment 0 base = 1400, segment 1 base = 6300, segment 2 base = 4300 (segment 2 มี limit = 400)

  1. อ้าง (segment 1, offset 300): 300 น้อยกว่า limit ผ่าน, physical = 6300 + 300 = 6600
  2. อ้าง (segment 2, offset 400): 400 ไม่ได้น้อยกว่า limit 400 (ต้องน้อยกว่าเท่านั้น) จึงเกิด error/exception ว่าการอ้างหน่วยความจำผิด

ข้อจำกัดของ segmentation คือกลับไปเจอ external fragmentation เพราะ segment เดียวต้องได้เนื้อที่ต่อเนื่อง ระบบเก่าจึงผสมทั้งสองแบบเป็น segmentation/paging: virtual address v = (s, p, d) คือ s ชี้ segment map table หา base ของ page table, p ชี้ PTE หา frame number, รวม frame + d เป็น real address อาจารย์สรุปว่า OS สมัยใหม่ใช้ paging เป็นหลัก ส่วน segmentation ที่โปรแกรมเมอร์เห็นเป็นเพียง logical segmentation เบื้องหลังเป็น paging ทั้งหมด

  • เงื่อนไขตรวจ limit ต้องเป็น "น้อยกว่า" เท่านั้น offset = limit ถือว่าผิด เช่น (segment 2, offset 400) เมื่อ limit = 400 ต้อง error

Virtual Memory (No.09 + คลิป 13.1 ถึง 13.3)

เรื่องต่อจาก real memory: ถ้า RAM เหลือน้อยกว่าขนาดโปรแกรม ยังรันได้ไหม คำตอบคือได้ ด้วยการโหลดเฉพาะบางเพจที่จำเป็น

ประเด็นสำคัญ
  • Virtual memory = แยก user logical memory ออกจาก physical memory โปรแกรมใหญ่กว่า RAM ที่มีจริงก็รันได้
  • Demand paging โหลดเพจเมื่อต้องใช้เท่านั้น, อ้างเพจที่ยังไม่อยู่ = page fault
  • Replacement: FIFO 15 / Optimal 9 / LRU 12 ครั้งบน reference string เดียวกันกับ 3 frame
  • Thrashing = วุ่นอยู่กับสลับเพจตลอด ตรวจด้วย working set: D = Σ WSSi ถ้า D > m ต้อง suspend process
  • ลูปเดินตาม row-major เกิด 128 faults ส่วนเดินข้ามแถวตลอดเกิด 16,384 faults

Virtual Memory กับ Demand Paging

Virtual memory คือการนำพื้นที่ storage (disk/SSD) มาทำหน้าที่เป็นหน่วยความจำส่วนหนึ่ง แยก user logical memory ออกจาก physical memory ในช่วงเวลาหนึ่งมีเพียงบางเพจของโปรแกรมอยู่ใน memory จริง logical address space จึงใหญ่กว่า physical ได้ และ physical address (frame) ถูกแชร์ระหว่าง process ได้ การสร้าง process ก็เร็วขึ้นเพราะไม่ต้องโหลดทั้งตัว

Implement ได้ 2 แบบ: demand paging และ demand segmentation OS ปัจจุบันใช้ paging วิชานี้จึงเรียนเฉพาะ demand paging ข้อดีของการโหลดเฉพาะเมื่อต้องใช้: ใช้ I/O น้อยลง, ใช้ memory น้อยลง, ตอบสนอง user เร็วขึ้น, รองรับ user พร้อมกันได้มากขึ้น

  • Lazy swapper = ไม่ swap เพจเข้า memory จนกว่าจะต้องใช้จริง swapper ที่ทำงานระดับเพจเรียกว่า pager
  • Valid-invalid bit ใน page table: v = เพจอยู่ใน memory แล้ว, i = ยังไม่อยู่ (ตอนเริ่มต้นทุก entry = i)
  • อ้างเพจที่ invalid มี 2 เคส: อ้างเพจที่ไม่มีสิทธิ์เลย = invalid reference ต้อง abort, ส่วนเพจที่มีสิทธิ์แต่ยังไม่ถูกโหลด = page fault (เคสที่วิชานี้สนใจ)

Page Fault: 6 ขั้นตอนจัดการ

ตัวอย่าง: โปรแกรม 8 เพจ มีอยู่ใน memory แค่ 3 เพจ (คลิป 13.1)
  1. โปรแกรมมี 8 เพจเก็บข้อมูล A ถึง H แต่มีเพียงเพจ 0, 2, 5 อยู่ใน memory (เพจ 0 = valid, เพจ 1 = invalid)
  2. โปรแกรมอ้างเพจ 1 เข้า page table พบว่า invalid เกิด interrupt ขึ้น OS ลุกขึ้นมาทำงาน
  3. OS ค้นใน storage ว่าเพจ 1 อยู่ตรงไหน แล้วดูว่ามี frame ว่างหรือไม่
  4. โหลดเพจ 1 จาก storage เข้า frame ว่าง
  5. อัปเดต page table: เก็บเลข frame และเปลี่ยน bit เป็น valid
  6. ให้คำสั่งเดิมที่ทำให้เกิด page fault ทำงานอีกครั้ง คราวนี้จะไม่ fault อีก

สรุปเป็น 6 ขั้นตอนตามสไลด์: (1) trap เข้า OS แล้วตรวจว่า reference ผิดหรือแค่ยังไม่อยู่ใน memory, (2) get empty frame, (3) swap page เข้า frame, (4) reset tables, (5) ตั้ง validation bit = v, (6) restart instruction ที่ทำให้เกิด fault ถ้าไม่มี free frame ต้องทำ page replacement ต่อ

ข้อผิดพลาดที่พบบ่อย: Belady's anomaly
  • Belady's anomaly = เพิ่มจำนวน frame แล้ว page fault กลับเพิ่มขึ้น อาจารย์เน้นว่าเกิดได้กับ FIFO จากการทดลองในคลิปมีบางจังหวะที่ "เพิ่ม frame แล้ว fault สูงขึ้น" แม้โดยทั่วไปยิ่งเพิ่ม frame ยิ่งลด
  • อย่าตอบว่า "เพิ่ม frame แล้ว fault ต้องลดเสมอ" ข้อสอบชอบดักประเด็นนี้กับ FIFO
  • Optimal ต้องมองอนาคต ถ้าโจทย์ให้เลือกแทนโดยดูเฉพาะอดีตแล้วตอบ Optimal คือผิด นั่นคือ LRU
  • ความต่าง LRU กับ FIFO อยู่ที่เกณฑ์ไล่: LRU ใช้ "ล่าสุดที่ถูกใช้" FIFO ใช้ "ลำดับที่เข้ามา" ผลลัพธ์ต่างกันเมื่อเพจถูกอ้างซ้ำแต่ไม่ถูกแทน

Global กับ Local allocation

  • Global replacement: เลือกเพจจาก process ไหนไปแทนก็ได้ ข้อดีคือเหมือนแต่ละ process มี memory ใหญ่ข้อเสียคือ process อาจโดนเพจถูก process อื่นแทนที่จนเกิด fault โดยไม่รู้ตัว
  • Local replacement: แทนที่เฉพาะ frame ที่จัดสรรให้ตัวเอง ข้อดีคืออัตรา fault ขึ้นกับตัว process เองเท่านั้น ข้อเสียคือเหมือนมี memory ให้ใช้น้อยลง

Thrashing

Thrashing = ปรากฏการณ์ที่ process ยุ่งอยู่กับ swap เพจเข้าออกระหว่าง storage กับ memory ตลอดเวลา อ้างเพจทีไรก็เกิด fault เพจเก่าถูกถอดไปเร็ว ๆ แล้วต้องเรียกคืน ผลคือ CPU ทำงานได้น้อยลงเพราะไปรอ I/O ตลอด ทำให้ CPU utilization ต่ำ เกิดได้ทั้งข้าม jobs (หลาย process แย่ง free frame ไม่กี่ frame) และภายใน job เดียว เช่น loop ที่ข้าม page boundary (cross page boundary)

กับดักวงจร thrashing ที่อาจารย์เน้น
  • ถ้า OS ไม่รู้ว่าเกิด thrashing จะเห็นแค่ CPU utilization ต่ำแล้วสรุปผิด ๆ ว่า "process น้อยไป" จึงเพิ่ม degree of multiprogramming โหลด process เข้ามาอีก ผลคือยิ่งแย่ เพราะ memory ยิ่งไม่พอ
  • อาการจริงคือ page-fault rate สูงมาก ไม่ใช่ CPU ขาดงาน ทางแก้จึงไม่ใช่เพิ่ม process

Working-Set Model

Working set = ชุดเพจของ process ที่เมื่ออยู่ใน memory พร้อมกันแล้วไม่ทำให้เกิด page fault อาศัยแนวคิด locality of reference (เพจที่ถูกเรียกใช้ซ้ำ ๆ บ่อย ๆ ในช่วงสั้น ๆ)

  • Δ (working-set window) = จำนวน page reference คงที่ที่ใช้พิจารณา (ตัวอย่างสไลด์: 10,000 instruction)
  • WSSi = จำนวนเพจที่ Pi อ้างถึงใน Δ ล่าสุด เปลี่ยนตามเวลา เพราะขึ้นกับพฤติกรรมโปรแกรมช่วงนั้น
  • Δ เล็กไป = ไม่ครอบ locality ทั้งหมด, Δ ใหญ่ไป = ครอบหลาย locality โดยไม่จำเป็น, Δ = อนันต์ = ครอบทั้งโปรแกรม
  • D = Σ WSSi = total demand frames ถ้า D > m (จำนวน frame ทั้งระบบ) เกิด thrashing แนวทางแก้คือ suspend process หนึ่ง เพื่อคืน frame
ตัวอย่าง: ตรวจ thrashing ด้วย D (คลิป 13.3)

กำหนด working set สูงสุดได้ 10 เพจต่อ process

  1. ที่เวลา T1: P1 อ้าง 10 เพจแต่มีเพจซ้ำ ต้องการจริงแค่ 5 เพจ, P2 ต้องการ 6 เพจ รวม D = 5 + 6 = 11
  2. ถ้าระบบมี frame ว่างอย่างน้อย 11 frame ก็ไม่เกิด thrashing ถ้าน้อยกว่านั้นเกิด thrashing ต้อง suspend process สักตัว
  3. ที่เวลา T2: P1 อ้าง 10 เพจแต่ของใหม่มีแค่เพจ 3 กับ 4 ต้องการจริงแค่ 2 เพจ, P2 ต้องการ 6 เพจ รวม D = 8 มี 8 frame ขึ้นไปก็พอ
  4. ข้อสรุป: ขนาด working set เปลี่ยนแปลงตามเวลา ต้องเช็คทุกช่วง

Program Structure กับ Page Fault: array 128 x 128

ตัวอย่าง: เติม 0 ลง array 2 มิติ 128 x 128 แบบไหนดีกว่า (สไลด์ + คลิป 13.3)
  1. กำหนด: int[128,128], แต่ละแถว (row) อยู่ใน 1 page, ภาษาส่วนใหญ่จัดเก็บแบบ row-major คือ fix แถวแล้วไล่คอลัมน์
  2. โปรแกรม 1: ลูป j (คอลัมน์) นอก, i (แถว) ใน คือเดินข้ามแถวทุกครั้ง เข้าถึงแต่ละตัวเปลี่ยนเพจตลอด เกิด fault ทุกครั้ง = 128 คอลัมน์ x 128 แถว = 16,384 page faults
  3. โปรแกรม 2: ลูป i (แถว) นอก, j (คอลัมน์) ใน คือเดินตาม row-major ภายในแถวเดียวกันไม่เกิด fault, fault เกิดเฉพาะตอนเปลี่ยนแถว = 128 page faults
  4. สองโปรแกรมให้ผลลัพธ์เหมือนกันแต่ fault ต่างกัน 128 เท่า บทเรียน: ลำดับการเข้าถึงข้อมูลตาม layout ของ memory สำคัญมาก เชื่อมกับตัวอย่าง a[1024][1024] ในคาบแรก
มักออกสอบ
  • นิยาม virtual memory + ประโยชน์ 4 ข้อ (I/O น้อย, memory น้อย, response เร็ว, รองรับ user มากขึ้น)
  • demand paging, lazy swapper/pager, valid-invalid bit ทำหน้าที่อะไร
  • ไล่ 6 ขั้นตอนจัดการ page fault ให้ครบ (trap, หา frame, swap in, reset tables, set valid, restart)
  • คำนวณจำนวน page fault ด้วย FIFO / Optimal / LRU จาก reference string กับ 3 frame: 15 / 9 / 12 และอธิบายได้ว่าทำไม Optimal ใช้จริงไม่ได้ (ต้องรู้อนาคต) จึงใช้เป็น benchmark
  • Belady's anomaly เกิดกับ algorithm ไหน (FIFO) และคืออะไร
  • global vs local replacement ข้อดีข้อเสีย
  • thrashing: นิยาม, สาเหตุ, วงจร CPU utilization ต่ำ, และเงื่อนไข D = Σ WSSi > m แก้ด้วยการ suspend process
  • โจทย์ array 128 x 128: 128 faults กับ 16,384 faults ต่างกันตรงลำดับลูป

File System (No.10 + คลิป 14.1 ถึง 14.3)

OS จัดการทรัพยากรอีกอย่างคือไฟล์บน storage หัวข้อนี้ไล่ตั้งแต่ file system ยอดนิยม, วิธีจัดสรร block, directory และ link, การ mount จนถึง permission

ประเด็นสำคัญ
  • FAT32 จำกัดไฟล์ 4 GB, NTFS/ext4 มี journaling, exFAT ไม่มี journaling, APFS มี snapshot + encryption
  • Allocation 3 แบบ: contiguous เร็วแต่ external fragmentation, linked ยืดหยุ่นแต่ pointer overhead + ช้า, indexed = index block + random access
  • Hard link ชี้ inode, ห้ามข้าม file system และห้ามชี้ directory, symbolic link เก็บ path เป็น shortcut แตกได้ (broken)
  • Mount = แนบ storage เข้า mount point, unmount ก่อนถอดอุปกรณ์
  • Permission = RWX x 3 กลุ่ม (owner, group, public), 7 = 111, 6 = 110, 1 = 001

File System ทำหน้าที่อะไร

File system = component ของ OS ที่จัดการการเก็บ/ดึง/จัดระเบียบข้อมูลบน storage (HDD, SSD, USB) และซ่อนความต่างของ hardware ให้ผู้ใช้เข้าถึงด้วยวิธีเดียวกัน หน้าที่หลัก: ตั้งชื่อและจัดโครงสร้างไฟล์ (โฟลเดอร์), เก็บ/อ่าน/แก้ไขข้อมูล, ดูแล metadata (ขนาดไฟล์, วันเวลา, permission), และ security/ควบคุมการเข้าถึง

File Allocation Methods

วิธีพื้นฐานมี 3 แบบ OS จริงเอาไปปรับปรุงหรือผสมกัน

วิธีหลักการข้อดีข้อเสีย
Contiguousไฟล์อยู่ block ติดกันเป็นผืนเดียว เก็บแค่ block เริ่ม + lengthง่าย อ่านไล่ลำดับเร็ว (seek น้อย)External fragmentation, ขยายไฟล์ยาก อาจต้อง defragment
Linkedไฟล์ = linked list ของ block แต่ละ block มี data + pointer ไป block ถัดไป เก็บ start/end blockไม่มี external fragmentation, ขยายไฟล์ง่ายเสียที่เก็บ pointer ต่อ block, เข้าถึงช้าต้องไล่ลูกโซ่, block กลางพัง = อ่านต่อทั้งไฟล์ไม่ได้
Indexedรวมทุก pointer ไว้ใน index block (1 ช่องชี้ 1 data block, ช่องว่างใส่ -1 แทนจบไฟล์)Random access ได้, ไม่มี external fragmentationเสีย storage ทำ index block

FAT (File-Allocation Table) คือ linked allocation ที่ดึง pointer ออกจาก data block มารวมไว้เป็นตาราง แก้ปัญหา pointer ปน data ของ linked แท้ ๆ

ตัวอย่าง: อ่านไฟล์ด้วย FAT (คลิป 14.2)
  1. ไฟล์ test เริ่มต้นที่บล็อก 217, อ่านข้อมูลบล็อก 217
  2. วิ่งดู FAT ช่อง 217 บอกว่าบล็อกถัดไปคือ 618 จึงอ่านบล็อก 618
  3. ดู FAT ช่อง 618 บอกต่อว่า 339 จึงอ่านบล็อก 339
  4. FAT ช่อง 339 ไม่มีค่า = จบไฟล์

ปัญหาของ FAT: FAT เก็บที่ sector ต้น ๆ ของ disk ต้องวิ่งไปกลับตลอด วิธีแก้คือโหลด FAT เข้า memory (RAM) แลกกับเปลือง memory และ OS เก็บ FAT สำรองอีกชุด ถ้าเสียทั้งคู่อาจอ่านไฟล์ทั้ง disk ไม่ได้เลย

ตัวอย่าง: ที่มาของขีดจำกัด FAT32 ไฟล์ 4 GB และ volume 8 TB (คลิป 14.2)
  1. ขนาดไฟล์ถูกจำกัดโดย field "file size" ใน directory entry ซึ่งใหญ่ 4 bytes จึงเก็บได้สูงสุด 2^32 bytes = 4 GB
  2. FAT table 1 entry มี 32 bits แต่ใช้จริงแค่ 28 bits อ้างเลขบล็อก (อีก 4 bits reserved) จึงอ้างได้สูงสุด 2^28 บล็อก
  3. ถ้าใช้บล็อกขนาด 32 KB = 2^15: volume ใหญ่สุด = 2^15 x 2^28 = 2^43 = 8 TB
  4. เกร็ด: ยิ่งใช้บล็อกใหญ่ (เช่น 32K) ยิ่งเกิด internal fragmentation มากขึ้น

ไฟล์ใหญ่จน index block เดียวไม่พอ และ combined scheme

  • Single level (linked index blocks): ช่องสุดท้ายของ index block ชี้ไป index block ถัดไปแทน data block ไฟล์ใหญ่ขึ้นได้เรื่อย ๆ แต่ไฟล์ใหญ่มากไม่มีประสิทธิภาพ
  • Multi-level: คิดเหมือน hierarchical paging สมมติบล็อก 512 word, 1 word เก็บ 1 pointer: outer index 512 ช่อง แต่ละช่องชี้ index table 512 ช่อง ที่ชี้ data block 512 word แบบ 2-level รองรับไฟล์ได้ถึง 512^3 word (ตรงกับเลข 512 ยกกำลังสามในสไลด์)
ตัวอย่าง: combined scheme (ฐานของ NTFS, ext) คำนวณขนาดไฟล์สูงสุด (คลิป 14.2)

block ขนาด 4 KB, pointer 4 bytes, inode มี pointer 15 ตัว: 12 direct + 1 single indirect + 1 double indirect + 1 triple indirect, 1 index block มี 4K / 4 = 1,024 ช่อง

  1. Direct 12 ตัว: 12 x 4 KB = 48 KB (ไฟล์ไม่เกิน 48 KB ใช้ direct พอ ไม่ต้องผ่าน indirect เลย)
  2. Single indirect: 1,024 ช่อง x 4 KB = 4 MB
  3. Double indirect: 1,024^2 บล็อก x 4 KB = 4 GB
  4. Triple indirect: 1,024^3 บล็อก x 4 KB = 4 TB
  5. รวมไฟล์ใหญ่สุด = 48 KB + 4 MB + 4 GB + 4 TB ประมาณ 4 TB กว่า ๆ

เหตุผลที่ใช้ combined แทน multi-level เดียว: ไฟล์เล็กไม่ควรผ่านหลาย level ทุกครั้งเพราะเข้าถึงช้าโดยไม่จำเป็น

Directory และการแชร์ไฟล์

Directory (folder) มองได้ว่าเป็นตารางแปลงชื่อไฟล์ (symbol table) ไปสู่ directory entry operations ที่ทำได้: search, create, delete, list, rename, traverse โครงสร้างของ OS ปัจจุบันเป็น tree เริ่มจาก root ไล่ลงไป แต่ tree แชร์ไฟล์ร่วมกันไม่ได้ (ไฟล์เดียวมี parent ได้ตัวเดียว) เมื่อต้องอ้างไฟล์เดียวกันจากหลายที่ โครงสร้างจึงเปลี่ยนเป็น acyclic graph (กราฟไม่มีวงวน) โดยใช้ link (pointer ไปยังไฟล์/subdirectory อื่น) ซึ่งเป็นวิธีที่ unix ใช้

  • ปัญหา aliasing: ไฟล์เดียวอ้างได้ด้วยหลาย absolute path เวลา traverse (นับไฟล์, copy, back up) ต้องไม่เข้าถึงไฟล์เดียวกันซ้ำ 2 ครั้ง
  • ปัญหาการลบ: ถ้าลบแล้วคืนพื้นที่ทันที link ที่เหลือกลายเป็น dangling pointer (ชี้ไฟล์ที่ไม่มีแล้ว และอาจชี้ทับไฟล์ใหม่โดยไม่ตั้งใจ)
  • ทางแก้คือ reference count: เพิ่ม link = +1, ลบ link = -1, count = 0 ค่อยลบไฟล์จริง unix implement ด้วย hard link
  • ถ้าโครงสร้างมี cycle (โฟลเดอร์ลิงก์วนกลับมาหาเดิม) traverse อาจวนติดรูป วิธีแก้ที่ง่ายกว่าคือตอนท่อง directory ให้ข้าม link ไปเลย (อีกทางคือ detect cycle แต่ช้า โดยเฉพาะบน disk)

File System Mounting

Mounting = ทำให้ file system เข้าถึงได้ โดยแนบ storage เข้ากับ directory หนึ่งที่เรียก mount point ใน directory tree เช่น `/mnt/usb`, `/media/usb` ฝั่ง Windows ไดรฟ์ C:, D: ก็คือ mount point OS หนึ่งตัวใช้หลาย file system พร้อมกันได้ เช่น SSD เป็น NTFS แต่เสียบ USB ที่เป็น FAT32 ก็ copy ไฟล์ได้ตามปกติโดยผู้ใช้ไม่ต้องรู้ความต่าง

  • คำสั่ง: `mount [OPTIONS] DEVICE MOUNT_POINT` เช่น `mount /dev/sdb1 /mnt/usb`, เลิกใช้: `umount /mnt/usb`
  • จากคลิป (บน Linux/WSL): `mkdir myd` แล้ว `sudo mount -t drvfs D: myd` (mount ต้องเป็น root จึงใช้ sudo, -t คือ file system type ที่นี่คือ drvfs) โฟลเดอร์ myd จะขึ้นสีเขียวและ ls myd เห็นไฟล์ของไดรฟ์ D ถอนด้วย `sudo umount myd`
  • Unmount ก่อนถอดอุปกรณ์ เพื่อให้ pending writes เสร็จและไม่มีไฟล์เปิดค้าง ยุคนี้ OS เก่งขึ้นถึงกับ mount ให้อัตโนมัติตอนเสียบ แต่หลักการยังเหมือนเดิม

Protection: Permission

หลักการคือเจ้าของไฟล์ควบคุมได้ว่า "ใคร ทำอะไรได้" มี mode of access 3 แบบ: read, write, execute (RWX) กับ 3 กลุ่มผู้ใช้: owner, group, public แปลงแต่ละกลุ่มเป็นเลขฐาน 8 ตัวอย่างจากสไลด์: 7 = 111 = rwx, 6 = 110 = rw-, 1 = 001 = --x

ตัวอย่าง: อ่านและตั้ง permission 755 และ 664 (คลิป 14.3)
  1. ไฟล์โปรแกรม client: เจ้าของ rwx = 1,1,1 กลุ่ม r-x = 1,0,1 คนอื่น r-x = 1,0,1
  2. แปลงเป็นฐาน 8: 111 = 7, 101 = 5, 101 = 5 ได้ 755 ความหมายคือเจ้าของทำได้ทุกอย่าง ส่วนกลุ่มกับคนอื่นอ่านกับ execute เท่านั้น
  3. เขียนเป็น 0755 ใส่ 0 นำหน้าเพื่อบอกว่าเป็นเลขฐาน 8 ไม่ใช่ฐาน 10 (เช่นใน `mkdir(ชื่อโฟลเดอร์, 0755)` ของ Standard C/POSIX)
  4. ไฟล์ใหม่ปกติเป็น rw- r-- r-- ถ้าอยากให้กลุ่มเขียนได้ด้วยแต่คนอื่นยังอ่านอย่างเดียว: 110 / 110 / 100
  5. แปลง: 110 = 6, 110 = 6, 100 = 4 ได้ 664 ใช้คำสั่ง `chmod 0664 ชื่อไฟล์` แล้วตรวจด้วย `ls -l`
มักออกสอบ
  • ตาราง file system: FAT32 ไฟล์ 4 GB, ตัวไหนมี journaling (NTFS, ext4) ตัวไหนไม่มี (exFAT, FAT32), APFS = snapshot + encryption, ใคร compatible ข้าม OS
  • ที่มาของ 4 GB (field file size 4 bytes = 2^32) และ 8 TB (28 bits x บล็อก 32 KB = 2^28 x 2^15)
  • เทียบ allocation 3 แบบ + FAT แก้อะไร, ทำไมควรโหลด FAT ขึ้น RAM
  • combined scheme: บล็อก 4 KB, pointer 4 bytes = 1,024 ช่องต่อ index block, 12 direct = 48 KB, single = 4 MB, double = 4 GB, triple = 4 TB รวมประมาณ 4 TB
  • tree vs acyclic graph, ปัญหาลบไฟล์ที่ถูกแชร์ (dangling pointer, reference count)
  • hard link vs symbolic link: inode, ข้าม filesystem, directory, broken link พร้อมคำสั่ง ln / ln -s
  • mount/umount และ mount point เช่น mount /dev/sdb1 /mnt/usb
  • แปลงเลข permission 7/6/1 และอ่านความหมาย 755, 664 กับ chmod
ข้อผิดพลาดที่พบบ่อย
  • exFAT ไม่มี journaling อย่าตอบว่าเป็นรุ่นใหม่แล้วมีทุกอย่างเหมือน NTFS
  • hard link ห้ามข้าม filesystem และห้ามชี้ directory สองข้อนี้เป็นจุดต่างที่ข้อสอบชอบถามเทียบกับ symbolic link
  • ลบไฟล์ต้นทางเมื่อไร symbolic link ไม่ได้หายไปด้วย แต่กลายเป็น broken link
  • 4 GB ของ FAT32 มาจาก field file size ใน directory entry ไม่ใช่จากความกว้างของ FAT entry (FAT entry จำกัดเรื่อง volume เป็น 8 TB)
  • linked allocation ถ้า block กลางไฟล์เสีย จะหา "block ถัดไป" ไม่เจอ อ่านส่วนที่เหลือทั้งไฟล์ไม่ได้

การติดตั้ง WSL2 (คลิปท้ายชุด)

WSL2 (Windows Subsystem for Linux 2) ใช้ให้เรียกคำสั่ง Linux บน Windows ได้ โดยไม่ต้องติดตั้งโปรแกรมจัดการเครื่องเสมือน (VMware/VirtualBox) แล้วค่อยลง Linux ทีหลัง เป็นสภาพแวดล้อมที่วิชานี้ใช้ทดลองคำสั่งต่าง ๆ

ตัวอย่าง: ขั้นตอนติดตั้งตามที่อาจารย์สาธิต
  1. ตรวจสอบเวอร์ชัน Windows ก่อน: ต้องเป็น Windows 10 version 2004 ขึ้นไป หรือ Windows 11
  2. เปิด PowerShell แบบ Run as Administrator (จะมีการยืนยันสิทธิ์)
  3. รันคำสั่ง wsl --install ระบบจะติดตั้ง WSL และดาวน์โหลด WSL kernel
  4. ระบบดาวน์โหลด Ubuntu มาให้เป็นค่าดีฟอลต์ แล้วรีบูตเครื่อง
  5. หลังรีบูตระบบติดตั้ง Ubuntu ต่อให้อัตโนมัติ ให้ตั้ง username ใหม่กับ password (อาจารย์เน้น: ต้องจำ password ให้ได้)
  6. ผลลัพธ์: ได้ WSL 2.0 พร้อม Ubuntu รุ่น LTS (long term support) ถ้าอยากใช้ distro อื่นมี option ให้เลือกติดตั้งได้

เกร็ดท้ายจากคลิป: ถ้าติดตั้งไปแล้วต้องการแก้ไขหรือติดตั้งเพิ่ม ทำตามขั้นตอนในหน้าเว็บทางการได้เลย ยุคนี้ติดตั้งง่ายกว่าสมัยก่อนมาก และจากหัวข้อ File System ด้านบน คำสั่ง `sudo mount -t drvfs D: myd` ก็ทดลองบน WSL ได้

มักออกสอบ
  • เงื่อนไขเวอร์ชัน: Windows 10 version 2004 ขึ้นไป หรือ Windows 11
  • คำสั่งติดตั้งคือ wsl --install ใน PowerShell แบบ Administrator และต้องรีบูตหลังติดตั้ง
  • distro ดีฟอลต์ที่ได้คือ Ubuntu รุ่น LTS และต้องตั้ง username/password
