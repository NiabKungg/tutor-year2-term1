วิชานี้เรียนอะไร

เรียน หลักการทำงานภาพรวมของ OS ไม่ใช่วิธี "ใช้งาน" ระบบปฏิบัติการ เครื่องมือของวิชาคือ Java และ C เขียนบน Linux (Ubuntu)

ประเด็นสำคัญ
  • OS ทำงานอย่างไรและควบคุมฮาร์ดแวร์/ซอฟต์แวร์อย่างไร, ทำไมเปิดหลายโปรแกรมพร้อมกันบนเครื่องเดียวได้
  • เราเขียนโปรแกรมติดต่อกับ OS อย่างไร (system call)
  • แนวคิด concurrent programming: หลายโปรแกรมเข้าไปแก้ข้อมูลตัวเดียวกันพร้อมกันแล้วข้อมูลเพี้ยน วิชานี้สอนปัญหาและวิธีแก้
  • เหตุผลเรียน: เป็น power user, เข้าใจความสัมพันธ์ Hardware (Computer Organization) กับ Software (OS), ฐานสำหรับงานผู้ดูแลระบบ/เครือข่าย และเป็นโปรแกรมเมอร์ที่ดีขึ้น

OS คืออะไร ประกอบด้วยอะไร

OS คือ software ที่จัดการ resources ของคอมพิวเตอร์และควบคุมว่าใครใช้ระบบอย่างไร เป้าหมายคือรันโปรแกรมผู้ใช้ให้ง่าย ทำระบบ user-friendly และเพิ่มประสิทธิภาพการใช้ฮาร์ดแวร์

  • Kernel = ส่วนแกนที่รับผิดชอบงานพื้นฐานของ OS เมื่อพูดถึง OS โดยพื้นฐานหมายถึง kernel
  • ส่วนที่เหลือคือ system programs และ application programs
  • องค์ประกอบ OS: Memory Manager, Processor Manager, Device Manager, File Manager, User Command Interface, Network Manager, Security Manager
  • ทุก component ต้อง monitor resources ของตน ทำตามกฎ "who gets what, when, and how much", allocate เมื่อเหมาะสม และ deallocate เมื่อจำเป็น

Boot Process (การบูตเครื่อง)

Booting คือการเริ่มเครื่องโดยการโหลด kernel ลำดับคือ: Power On (CPU รันคำสั่งจาก BIOS/UEFI) → POST (Power-On Self-Test ตรวจฮาร์ดแวร์) → เลือก boot loader (BIOS มองหา MBR, UEFI มองหา ESP และอ่าน BCD) → รัน bootloader → โหลด OS kernel → OS initialization

Dual Mode Operation

  • Mode bit = hardware flag บอกโหมดปัจจุบัน: 0 = kernel (monitor) mode, 1 = user mode
  • เกิด interrupt/fault เมื่อใด hardware จะสลับเข้า monitor mode ให้เอง
  • Privileged instructions ใช้ได้เฉพาะใน monitor mode เท่านั้น

Computer-System Operation และ Interrupt

  • I/O devices กับ CPU ทำงานพร้อมกัน (concurrently) ได้ แต่ละ device controller ดูแล device ประเภทหนึ่ง เมื่อทำงานเสร็จจะ ขัดจังหวะ (interrupt) CPU
  • OS เป็น interrupt driven: save address ของคำสั่งที่ถูกขัด แล้วส่ง control ไปยัง interrupt service routine ผ่าน interrupt vector (เก็บ address ของทุก service routine)
  • Trap = interrupt ที่เกิดจาก software ทั้งจาก program error (exception) และการขอบริการ OS ผ่าน system call

ประเภทของ OS

  • ตามวิธีป้อนข้อมูล: Batch (Single/Multi-programmed, jobs ประมวลผลตามลำดับ automatic job sequencing, ไม่มีปฏิสัมพันธ์กับผู้ใช้), Interactive (เกิดจากโปรแกรมเมอร์ต้องแก้ bug เร็ว ๆ ต้องมี time-sharing), Hybrid (ผสม รัน batch ตอน workload interactive ต่ำ)
  • ตามจำนวน user/task: Single-user single-tasking (MS-DOS), Single-user multi-tasking (desktop/laptop), Multi-user multi-tasking (server)
  • Special purpose: Hard real-time (secondary storage จำกัดหรือไม่มี เก็บข้อมูลใน short-term memory หรือ ROM, เข้ากันไม่ได้กับ time-sharing และ general-purpose OS, ตัวอย่าง VxWorks, RTXC), Soft real-time (multimedia, virtual reality), Embedded (คอมพิวเตอร์เฉพาะงาน resource จำกัด)
  • ตามสถาปัตยกรรม: Single Processor, Parallel/Multiprocessor (tightly-coupled เช่น dual-core), Distributed (หลายเครื่องอิสระรวมกันเป็นระบบเดียว, loosely-coupled, ต้องมี network; แบ่งเป็น Network OS เช่น Windows Server, Ubuntu Server และ Distributed OS เช่น Sprite, Amoeba)

บริการของ OS ที่ต้องจำ: User interface (CLI/GUI/Batch), Program execution, I/O operations, File-system manipulation, Communications, Error detection, Resource allocation, Accounting, Protection and security (Protection = ควบคุมการเข้าถึง resource, Security = user authentication + ป้องกัน I/O ภายนอก)

Process (กระบวนการ)

Program vs Process

  • Program = inactive entity คือไฟล์เก็บบนดิสก์
  • Process = program in execution เป็น active entity ต้องใช้ resources และมีข้อมูลของตัวเอง: program counter, stack, data section
  • Process คือ single instance ของ executable; ใน time-sharing system เรียก Task ใน batch system เรียก Job
  • สไลด์มีแผนภาพ Process State และ Seven-State Process Model (รุ่นสถานะ process 7 สถานะ)

Scheduling Queues

  • Job queue = process ทั้งหมดในระบบ
  • Ready queue = process ที่อยู่ใน main memory พร้อมรอรัน
  • Device queues = process ที่รอ I/O device
  • Process ย้ายไปมาระหว่าง queues ได้เรื่อย ๆ

PCB, Context Switch และ Dispatcher

  • PCB (Process Control Block) = โครงสร้างข้อมูลที่เก็บ context ของ process
  • Context switch: เมื่อ CPU เปลี่ยนไปรัน process อื่น ต้อง save state เดิม + load state ใหม่ (อ้างอิงข้อมูลใน PCB) เป็น overhead เพราะระหว่างสวิตช์ระบบไม่ทำงานที่เป็นประโยชน์ ระยะเวลาขึ้นกับ hardware support
  • Dispatcher ส่ง CPU ให้ process ที่ short-term scheduler เลือก โดย: switch context → สลับเป็น user mode → jump ไปตำแหน่งเดิมของ user program
  • Dispatch latency = เวลาที่ dispatcher ใช้หยุด process หนึ่งแล้วเริ่มอีก process หนึ่ง

Process Creation: fork/exec/wait

Parent process สร้าง child process ทำให้เกิด process tree กลไกหลักใน UNIX คือ fork() กับ exec()

pid_t pid = fork();
if (pid < 0) {                       /* ติดลบ = สร้างไม่สำเร็จ */
    fprintf(stderr, "Fork failed");
} else if (pid == 0) {               /* ใน child: pid == 0 */
    execlp("/bin/ls", "ls", NULL);   /* exec: แทนที่ process image ด้วยโปรแกรมใหม่ */
} else {                             /* ใน parent: pid = process id ของ child (> 0) */
    wait(NULL);                      /* รอลูกจบแล้วค่อยทำงานต่อ */
}
  • fork() สร้าง child โดย copy ตัวเอง แล้วทั้ง parent และ child รันต่อจากจุดเดียวกัน
  • ค่าที่คืน: child ได้ 0, parent ได้ process ID ของ child (> 0), ติดลบ = สร้างไม่สำเร็จ
  • ตัวแปร (เช่น i) ถูก copy แยกระหว่าง parent/child และลำดับ output เป็น non-deterministic ดูโค้ดแล้วเดาลำดับไม่ได้
  • exec() = ครอบครัวฟังก์ชันที่แทนที่ process image เดิมด้วยโปรแกรมใหม่ทั้งหมด
  • แพตเทิร์นคลาสสิก: fork() → ลูก execlp → parent wait(NULL) แล้วค่อยทำงานต่อ

Process Termination

  • Process จบด้วยคำสั่งสุดท้าย + ขอให้ OS ทำลาย (exit), ส่ง output ไป parent ผ่าน wait, OS คืน resources
  • Parent อาจ abort child เมื่อ: child ใช้ resource เกินที่จัดสรร / งานที่มอบหมายไม่ต้องใช้แล้ว / parent กำลังจะจบ
  • Cascading termination: บาง OS ไม่ให้ child อยู่ต่อถ้า parent จบ child ทั้งหมดจึงถูก terminate ตาม

Process ใน Java

JVM เป็นแอปธรรมดาที่รันเป็น process เดียว บน host OS และ Java ไม่รองรับ process model (สร้างหลาย process ใน JVM เดียวไม่ได้) แต่ใช้ class ProcessBuilder สร้าง process ภายนอกของ OS ได้

Thread

นิยามและเทียบกับ Process

Thread คือส่วนของโปรแกรมที่รันได้อย่างอิสระจากส่วนอื่น คือลำดับคำสั่งที่ทำงานอยู่ ภายใน process เดิม ไม่ได้สร้าง process ใหม่เหมือน fork จึงเรียกว่า lightweight process

  • สิ่งที่ thread แต่ละตัวต้องมีเป็นของตัวเอง: program counter, registers, stack
  • Thread ใน process เดียวกัน แชร์ code, data และ open files ร่วมกัน (fork แบบ process จะ copy ทุกอย่างจึงใช้ทรัพยากรเยอะกว่า)
  • เพราะฉะนั้น สลับ (swap) thread เร็วและถูกกว่าสลับ process, thread คือ element ที่ใช้ CPU และถูกจัดคิวรัน, multithreaded app มีหลาย thread รันพร้อมกันด้วย priority เท่ากันหรือต่างกันได้

Thread State และ TCB (จากคลิป 5.1)

  • Thread state: New → Runnable (เทียบเท่า Ready) → Running → Terminated มี Blocked กับ Timed waiting (waiting ที่แบ่งละเอียดขึ้น: timed waiting = sleep รอตามเวลา, blocked = รอทรัพยากร)
  • จุดที่อาจารย์เน้น: พอรอเสร็จทุกกรณี กลับไปที่ Runnable (Ready) เสมอ ไม่ได้กลับเข้า Running โดยตรง
  • TCB (Thread Control Block) เก็บ: thread ID, สถานะ, program counter, ค่า register, priority และ pointer ชี้ไปยัง process ที่สร้างมัน

User-Level Thread vs Kernel-Level Thread และโมเดลการจับคู่

  • ULT: จัดการด้วย thread library ฝั่งผู้ใช้ มี 3 libraries: POSIX Pthreads, Win32 threads, Java threads
  • KLT: OS สมัยใหม่ support โดย kernel ทั้งสองแบบต้องจับคู่กันในการทำงานจริง

  • อย่าเขียนโปรแกรมโดยสมมติลำดับการรันของ thread (ยืนยันอีกครั้งในหัวข้อ Java Scheduling ของ CPU Scheduling)

Pthreads: โปรแกรม multithread ด้วย C (คลิป 5.2)

โจทย์ตัวอย่าง: ผู้ใช้ป้อนเลข n → thread ลูกหาผลรวม 1..n เก็บใน sum → thread แม่ (main) เป็นคนพิมพ์ค่าออกมา แสดงว่าแม่กับลูกใช้ข้อมูลร่วมกันได้จริง

int sum;                      /* global variable: อยู่ใน Data section ที่เทรดแชร์กัน */

void *runner(void *param);    /* prototype ตายตัว: คืนค่า void* รับพารามิเตอร์ void* 1 ตัว */

int main(int argc, char *argv[]) {
    pthread_t tid;                /* thread id ไม่ซ้ำกันแต่ละเทรด */
    pthread_attr_t attr;          /* attribute ของเทรด */
    pthread_attr_init(&attr);     /* ตั้งค่า default attribute */
    pthread_create(&tid, &attr, runner, argv[1]);
    /* 4 พารามิเตอร์: (1) &tid = OS ส่ง tid กลับมา (2) &attr = ใช้ default
       (3) runner = ฟังก์ชันที่ลูกจะทำ (4) argv[1] = ค่าส่งให้ runner */
    pthread_join(tid, NULL);      /* แม่รอลูก (เทียบเท่า wait), NULL = ไม่สนค่าที่ลูกส่งกลับ */
    printf("sum = %d\n", sum);    /* คนคำนวณคือลูก แต่คนพิมพ์คือแม่ */
}

void *runner(void *param) {
    int upper = atoi(param);      /* รับ string แปลงเป็น int */
    sum = 0;
    for (int i = 1; i <= upper; i++) sum += i;
    pthread_exit(NULL);           /* จบเทรด (ค่าส่งกลับเป็น pointer ต่างจาก exit ของ process) */
}
  • pthread_exit() ต่างจาก exit() ของ process ตรงที่ค่าส่งกลับเป็น pointer (ส่ง struct ซับซ้อนได้)
  • Compile ต้องลิงก์ pthread library: gcc pthread.c -o pthread -lpthread, รัน ./pthread 5 ได้ 15
  • ตัวอย่างที่ 2: ลูกจอง memory เองแล้วส่ง pointer กลับผ่าน pthread_exit แม่รับด้วย pthread_join(tid, &sum) แล้วพิมพ์ *sum อาจารย์ย้ำว่าทำได้จริง แต่ทางปฏิบัติไม่นิยม

Java Thread (คลิป 5.3)

สร้าง thread ใน Java ได้ 2 ทาง เลือกทางไหนก็ได้ ยกเว้นกรณี class สืบทอด class อื่นอยู่แล้ว Java ไม่รองรับ multiple inheritance จึง บังคับใช้ implements Runnable

/* วิธีที่ 1: extends Thread */
class Worker1 extends Thread {
    public void run() {                       /* override run(): งานของเทรดอยู่ที่นี่ */
        System.out.println("I am a worker thread");
    }
}
/* เรียกใช้: worker.start();  start() จะเรียก run() ผ่าน polymorphism */

/* วิธีที่ 2: implements Runnable */
class Worker2 implements Runnable {
    public void run() { System.out.println("I am a worker thread"); }
}
/* เรียกใช้: Thread t = new Thread(worker); t.start();  ห่อด้วย Thread object ก่อน */
  • ผลลัพธ์มี 2 บรรทัด (แม่ + ลูก) แต่ ไม่การันตีว่าใครพิมพ์ก่อน รันหลายครั้งอาจได้ลำดับต่างกัน
  • join() = แม่รอลูกจบ: "worker done" จะออกหลัง "worker working" เสมอเมื่อมี join
  • Java thread state: NEW → RUNNABLE (แปลว่า Ready ไม่ใช่กำลังรัน) → RUNNING → TERMINATED + Sleeping/Waiting/Blocking

Thread Cancellation (คลิป 5.4)

  • Asynchronous: ถูกสั่ง cancel ปุ๊บจบทันที
  • Deferred: thread ทำงานต่อจนถึง cancellation point (จุดที่ปลอดภัย) ค่อยจบ เช่นคำสั่ง I/O อย่าง printf, sleep หรือเรียก pthread_testcancel() เอง (Java ใช้แนวคิดเดียวกัน: interrupt() + ลูกต้องเช็ค isInterrupted() เอง ถ้าไม่เช็คก็ไม่หยุด เป็น cooperative mechanism)
void *worker(void *arg) {
    pthread_setcanceltype(PTHREAD_CANCEL_DEFERRED, NULL);  /* หรือ ASYNCHRONOUS */
    pthread_setcancelstate(PTHREAD_CANCEL_ENABLE, NULL);   /* default คือ ENABLE ตั้งหรือไม่ตั้งก็ได้ */
    while (1) { i++; }        /* ถ้า loop ไม่มี cancellation point, cancel แบบ deferred ไม่มีวันทำงาน */
    printf("thread finish work");
}
/* main: pthread_cancel(tid) สั่ง cancel แล้ว pthread_join(tid, NULL) รอให้จบ */
  • ทดลอง 4 สถานการณ์ของอาจารย์: deferred + loop ไม่มีจุด cancel → cancel ไม่ได้ต้อง Ctrl-C; ใส่ printf ใน loop → จบได้; asynchronous → หยุดทันที; ตั้ง cancel state เป็น DISABLE → ต่อให้ asynchronous ก็ cancel ไม่ได้
  • Default ของ Pthread คือ deferred เพราะ ปลอดภัยกว่าในแง่การใช้ทรัพยากร cancellation point ให้โอกาส thread เคลียร์ทรัพยากรก่อนจบ

Thread Pool (คลิป 5.4)

สร้าง thread ไว้ล่วงหน้าหลายตัว มีงานก็หยิบจาก pool ทำเสร็จกลับเข้า pool ข้อดีคือใช้ thread ที่มีอยู่เร็วกว่าสร้างใหม่ และจำกัดจำนวน thread ได้ Pthread ไม่มี thread pool ให้ใช้ ต้องสร้างเอง ส่วน Java มี 3 แบบ:

  • Single thread executor (pool ขนาด 1)
  • Fixed thread executor (ขนาดคงที่ ไม่เพิ่มไม่ลด)
  • Cached thread pool (dynamic: ตัวที่ idle 1 นาทีถูกถอดออก ต้องการมากขึ้นก็สร้างเพิ่ม)
ตัวอย่าง: ทดลอง 10,000 tasks (งานละ พิมพ์ชื่อ + sleep 1 วินาที)
วิธีเวลาที่วัดได้หมายเหตุของอาจารย์
ไม่ใช้ pool (สร้าง 10,000 เทรด)ประมาณ 3,444 ms
Unbounded poolประมาณ 2.6 วินาทีเร็วสุด เพราะเทรดที่ทำเสร็จกลับเข้า pool รับงานต่อได้เลย
Single-thread poolช้ามาก ต้องยกเลิกกลางทางทำทีละงาน มีสิทธิ์รอถึง 10,000 วินาที
Fixed 10,000ประมาณ 3.38 วินาทีช้ากว่าไม่ใช้ pool ซะอีก ขึ้นกับ implementation ที่ค่อย ๆ สร้างเทรดเมื่อจำเป็น
Fixed 1,000ประมาณ 10.2 วินาที
Fixed 5,000ประมาณ 2.9 วินาทีใกล้เคียง unbounded งานจริงต้องปรับขนาดให้เหมาะกับงานเรา
มักออกสอบ
  • นิยาม thread, สิ่งที่ thread มีเอง (PC, registers, stack) กับสิ่งที่แชร์ (code, data, open files), เหตุผลที่สลับ thread ถูกกว่า process
  • ตาราง 4 ประเภท OS ตาม process/thread (DOS, JVM, traditional UNIX, modern OS)
  • โมเดล many-to-one / one-to-one / many-to-many: ข้อดีข้อเสีย + ตัวอย่าง OS (Windows NT+/Linux/Solaris 9+, Solaris < 9, Tru64)
  • Thread state: รอเสร็จกลับ Runnable เสมอ, ข้อมูลใน TCB
  • พารามิเตอร์ของ pthread_create, pthread_join = wait, pthread_exit ส่ง pointer, compile ต้อง -lpthread
  • สร้าง Java thread 2 วิธี + กรณีบังคับใช้ Runnable (multiple inheritance), start() เรียก run() ผ่าน polymorphism
  • Cancellation: asynchronous vs deferred, cancellation point, default ของ Pthread คือ deferred, Java interrupt() ต้องให้ลูกร่วมมือเช็คเอง
  • Thread pool 3 แบบของ Java + บทเรียนจากทดลอง 10,000 tasks
ข้อผิดพลาดที่พบบ่อย
  • "สร้าง 10,000 เทรด เทรดละ 1 วินาที ทำไมไม่ใช้เวลา 10,000 วินาที" เพราะเทรดทั้งหมด ไม่ได้เข้าคิวต่อกันทำ แต่ทำงานพร้อมกัน ยิ่ง multicore ยิ่งเร็ว จึงจบในราว 3 วินาที
  • Fixed pool ขนาดใหญ่ไม่ได้แปลว่าเร็วสุดเสมอ (fixed 10,000 ช้ากว่าไม่ใช้ pool) ต้องลองปรับดู

CPU Scheduling

พื้นฐานและเกณฑ์วัด

CPU scheduler เลือก process จากพวกที่ ready แล้วให้ CPU แบ่งเป็น non-preemptive (เลือกแล้วขัดจังหวะไม่ได้ process ต้องยินดีปล่อย CPU เอง สมัยก่อนจึงต้องพึ่ง cooperative programming) กับ preemptive (OS ขัดจังหวะได้ตามต้องการ)

เกณฑ์เพิ่มประสิทธิภาพ 5 ข้อ
  • Max CPU utilization: ใช้ CPU ให้เต็มประสิทธิภาพ ไม่ปล่อยว่าง
  • Max throughput: จำนวน process ที่จบได้ต่อช่วงเวลามากที่สุด
  • Min turnaround time: นับจากส่ง process เข้ามาจนทำงานจบ ต้องน้อยสุด
  • Min waiting time: เวลาที่รออยู่ใน ready queue ต้องน้อยสุด
  • Min response time: นับจากป้อนคำสั่งจนมีการตอบสนองกลับครั้งแรก (ไม่ต้องจบงาน) ต้องน้อยสุด

อาจารย์บอกว่าวิชานี้เน้นด้านเวลา โดยเฉพาะ turnaround กับ waiting และมีสูตรตรวจคำตอบที่ใช้ได้กับทุกอัลกอริทึม:

สูตรสำคัญ (อาจารย์สอนในคลิป 6.1.1)
  1. turnaround time = เวลาจบ - เวลามาถึง (arrival)
  2. waiting time = turnaround time - burst time สำหรับอัลกอริทึมซับซ้อน หา turnaround ก่อนแล้วลบ burst จะง่ายกว่าอ่านจาก Gantt

FCFS (First-Come, First-Served) เป็น non-preemptive

ข้อมูล: P1 มาเวลา 0 ใช้ 24, P2 มาเวลา 2 ใช้ 3, P3 มาเวลา 4 ใช้ 3

| P1 (0-24) | P2 (24-27) | P3 (27-30) |
0           24           27           30
  • Waiting: P1 = 0, P2 = 24-2 = 22, P3 = 27-4 = 23 → เฉลี่ย 15
  • Turnaround: P1 = 24, P2 = 27-2 = 25, P3 = 30-4 = 26 (ตรวจด้วยสูตร turnaround - burst ได้ 0, 22, 23 ตรงกัน)

ถ้าสลับลำดับให้ตัวเล็กมาก่อน (P2 มา 0, P3 มา 2, P1 มา 4):

| P2 (0-3) | P3 (3-6) | P1 (6-30) |
0          3          6           30
  • Waiting: P2 = 0, P3 = 1, P1 = 2 → เฉลี่ย 1 (ดีขึ้นจาก 15 มหาศาล) turnaround ของ P1 แย่ขึ้นเป็น 26 แต่รวมทั้งระบบดีกว่า
  • Convoy effect = short process ต่อแถวหลัง long process ทำให้ทั้งระบบรอนาน อุปมาของอาจารย์: ไปธนาคารต่อคิวหลังคนทำธุรกรรมหลักล้าน คนทำธุรกรรมหลักพันทั้งคิวต้องรอตาม

SJF (Shortest-Job-First) เป็น non-preemptive

เลือก process ที่ใช้ burst time น้อยสุดทำก่อน SJF เป็น optimal ให้ average waiting time ต่ำสุดสำหรับชุด process ที่กำหนด แต่ทางปฏิบัติทำได้ยากเพราะไม่รู้ว่าแต่ละ process จะใช้ burst เท่าไร

ตัวอย่าง: P1(0,7), P2(2,4), P3(4,1), P4(5,4) เวลา 0 มีแต่ P1 และ SJF ไม่ขัดจังหวะ → P1 ทำจนจบก่อน

| P1 (0-7) | P3 (7-8) | P2 (8-12) | P4 (12-16) |
0          7          8           12           16
  • เวลา 7 คิวมี P2(4), P3(1), P4(4) เลือก P3 ตามด้วย P2 กับ P4 burst เท่ากัน เสมอกันเลือกตัวมาก่อน (tie-breaking)
  • Waiting: P1 = 0, P2 = 8-2 = 6, P3 = 7-4 = 3, P4 = 12-5 = 7 → เฉลี่ย 4; turnaround: 7, 10, 4, 11

SRTF (Shortest-Remaining-Time-First) เป็น preemptive ของ SJF

ถ้า process ใหม่เข้ามาและใช้เวลาน้อยกว่าเวลาคงเหลือ (remaining) ของตัวที่กำลังรัน → ขัดจังหวะแล้วสลับ ข้อเสีย: ใช้ใน interactive system ไม่ได้ (ต้องรู้ burst ล่วงหน้า) และ overhead มากกว่า SJF เพราะต้องคอยติดตาม CPU time แล้วทำ context switch

ชุดข้อมูลเดิม ไล่ได้:

| P1 (0-2) | P2 (2-4) | P3 (4-5) | P2 (5-7) | P4 (7-11) | P1 (11-16) |
0          2          4          5           7           11           16
  • เวลา 2, P2 มา (burst 4) ขณะ P1 เหลือ 5 → ขัด P1; เวลา 4, P3 มา (burst 1) ขณะ P2 เหลือ 2 → ขัด P2; เวลา 5 เหลือ P1(5), P2(2), P4(4) → P2 ต่อ แล้ว P4 ปิดท้าย P1
  • Waiting: P1 = 16-7 = 9, P2 = 5-4 = 1, P3 = 0, P4 = 7-5 = 2 → เฉลี่ย 3 (ดีกว่า SJF); turnaround: 16, 5, 1, 6
ข้อผิดพลาดที่พบบ่อย
  • ตอนใช้สูตร waiting = turnaround - burst ของ SRTF: waiting ของ P1 = 16 - 7 (burst ทั้งหมดของ P1 ไม่ใช่เศษ 5) = 9 อาจารย์เตือนจุดนี้เป็นพิเศษ

Priority Scheduling

  • ให้ CPU กับ process priority สูงสุด ทำ preemptive หรือ non-preemptive ก็ได้
  • ข้อควรระวังตัวเลข: ขึ้นกับ OS ด้วย Unix-based เลขสูง = สิทธิต่ำ แต่ Java thread กลับกัน เลขสูง = สิทธิสูง
  • มอง SJF ได้ว่าเป็น priority scheduling ที่ priority = predicted next CPU burst
  • ปัญหา Starvation: process สิทธิต่ำอาจไม่ได้รันเลยเพราะมีสิทธิสูงส่งเข้ามาตลอด ทางแก้ Aging: ยิ่งรอนานยิ่งเพิ่ม priority

Round Robin (RR) เป็น preemptive

  • แบ่งเวลา CPU เป็น time quantum (ปกติ 10-100 ms แล้วแต่ OS) ทำจบก่อนหมด quantum ก็จบไปเลย หมด quantum แล้วยังไม่จบ → ถูกขัดไปต่อท้าย ready queue
  • การรับประกัน: n process ใน ready queue, quantum = q → แต่ละ process รอไม่เกิน (n-1) x q เช่น n = 10, q = 100 ms → ตัวท้ายสุดรอไม่เกิน 900 ms
  • q ใหญ่เกิน → กลายเป็น FCFS; q เล็กเกิน → context switch ถี่เกิน เกิด overhead (q ต้องใหญ่พอเทียบกับ context-switch time) ตัวอย่าง process ใช้ 10 หน่วยเวลา: q = 12 → switch 0 ครั้ง, q = 6 → 1 ครั้ง, q = 1 → 9 ครั้ง

ตัวอย่าง q = 4 กับ P1(0,24), P2(2,3), P3(4,3): P1 ทำ 0-4 หมดเวลาออก ตอนเวลา 4 ทั้ง P2, P3 มาถึงแล้ว โดย P2 มาก่อน (เวลา 2) จึงได้ทำก่อน

| P1 0-4 | P2 4-7 | P3 7-10 | P1 10-14 | P1 14-18 | P1 18-22 | P1 22-26 | P1 26-30 |
0        4        7         10         14         18         22         26         30
  • Turnaround: P1 = 30, P2 = 7-2 = 5, P3 = 10-4 = 6; Waiting (turnaround - burst): P1 = 6, P2 = 2, P3 = 3
  • โดยทั่วไป turnaround เฉลี่ยสูงกว่า SJF แต่ response ดีกว่า เหมาะกับระบบ interactive

Multilevel Queue (MLQ) และ Multilevel Feedback Queue (MLFQ)

  • MLQ: แบ่ง ready queue เป็นหลายคิว แต่ละคิวใช้อัลกอริทึมของตัวเอง เช่น foreground (โต้ตอบ) ใช้ RR, background ใช้ FCFS ข้อจำกัด: process เข้าคิวไหนอยู่คิวนั้นตลอด ไม่ย้ายข้าม queue
  • จัดคิวระหว่าง queue ได้ 2 วิธี: fixed-priority (foreground ก่อน background เสี่ยง starvation) หรือ time slice (เช่น 80% foreground RR, 20% background FCFS)
  • MLFQ: process ย้ายข้าม queue ได้ จึงทำ aging ได้ ถ้าจะ implement ต้องออกแบบ: แบ่งกี่คิว, แต่ละคิวใช้อัลกอริทึมอะไร, วิธี promote/demote, process ใหม่เริ่มที่คิวไหน
ตัวอย่าง MLFQ 3 คิว (สไลด์ + คลิป 6.1.4)
  1. Q0 = RR quantum 8 ms → ไม่จบย้ายลง Q1 = RR quantum 16 ms → ยังไม่จบย้ายลง Q2 = FCFS
  2. ทุก process เข้า Q0 ก่อน ที่ Q2 หมายถึง "ใครมาก่อนได้รันก่อน" และได้ทำเมื่อ Q0, Q1 ว่าง พอได้ทำจะทำจนจบ
  3. ออกแบบนี้เหมาะกับงานสั้น: ใช้ 8 ms หรือน้อยกว่าจบที่ Q0, 8-24 ms จบที่ Q1, มากกว่า 24 ms ไปรอที่ Q2
  4. ข้อควรระวัง: หลายคิว = ซับซ้อนขึ้น OS ต้องบริหารไม่ให้เกิด starvation

Java Thread Scheduling (คลิป 6.2)

  • สเปกของ Java ไม่กำหนดวิธี scheduling มาตรฐาน ขึ้นกับแต่ละ JVM (JVM เรียกใช้ thread library ของ host OS) จึงเชื่อมกับข้อเตือนใน หัวข้อ Thread
  • กฎเหล็กที่อาจารย์เน้นหนักสุด: ห้ามเขียนโปรแกรม multithread โดยให้ความถูกต้องขึ้นอยู่กับ scheduling algorithm ถ้าต้องประสานงานจริงต้องใช้ synchronization (ดู หัวข้อ Synchronization)
  • ปกติเป็น preemptive + priority-based: priority 1-10, default 5 (setPriority()) เท่ากันเลือกแบบสุ่ม และการ set priority ไม่ได้รับประกันว่าสูงจะทำก่อนต่ำ มันแค่บอก JVM ว่าถ้าจำเป็นต้องเลือกให้เลือกตัว priority สูงกว่า
  • เทรดที่รันอยู่จะรันต่อจนกว่า 1 ใน 3 เหตุการณ์: มีเทรด priority สูงกว่าเข้ามา / เทรดเรียก yield() (ยังไม่จบงานแต่ยินดีออกจาก CPU ให้เทรด priority เท่ากัน) / ทำงานจบเอง หรือหมด time slice (ถ้าระบบ support time-slicing)
มักออกสอบ
  • เกณฑ์วัด 5 ข้อพร้อมนิยามที่ต่างกันของ turnaround/waiting/response + สูตร waiting = turnaround - burst
  • คำนวณ Gantt + waiting/turnaround ให้ครบ: FCFS เฉลี่ย 15 (สลับคิวได้ 1), SJF เฉลี่ย 4, SRTF เฉลี่ย 3, RR q=4 waiting 6/2/3
  • convoy effect, tie-breaking ของ SJF (burst เท่ากันเลือกตัวมาก่อน), การตัดสินใจขัดจังหวะของ SRTF (เทียบ remaining time)
  • starvation/aging ของ priority, ต่างกันไหมเลขสูงคือสิทธิสูง (Unix กับ Java ตรงกันข้าม)
  • กฎ (n-1)q ของ RR, q ใหญ่ = FIFO, q เล็ก = context switch บ่อย
  • ต่างกันของ multilevel queue (ไม่ย้ายคิว) กับ multilevel feedback queue (ย้ายคิวได้ + aging) + ตัวอย่าง Q0 8ms / Q1 16ms / Q2 FCFS
  • Java: spec ไม่กำหนด scheduler, priority 1-10 default 5, 3 เหตุการณ์ที่เทรดหลุดจาก CPU, yield()

IPC และ Signal

Inter-Process Communication: ภาพรวม

Process ในระบบแบ่งเป็น independent (อิสระต่อกัน) หรือ cooperating (การทำงานของ process หนึ่งกระทบอีก process และ/หรือแลกเปลี่ยนข้อมูลกัน) เหตุผลที่ต้อง cooperate มี 3 ข้อ: Information sharing, Computation speedup, Modularity (แต่ละ process รับผิดชอบ module ของตัวแล้วเอาผลมารวมกัน)

OS แทบทุกตัวเตรียมกลไก IPC พื้นฐานไว้ 3 โมเดล: Signal, Shared memory, Message passing (UNIX มีให้: Signal, Pipe, Shared memory)

กลไกใช้ทำอะไรข้อดี/ข้อจำกัด (จากคลิป 7.1)
Signalแจ้งเตือนว่าเกิด eventพกข้อมูลได้น้อยมาก (แค่ signal number) ใช้ส่งข้อมูลจริงไม่ได้
Message passingส่งข้อมูลจริงผ่าน message boxmessage box อยู่ใน kernel ต้องสลับ user/kernel mode จึงช้า แต่ OS จัดการ synchronization ให้ ข้ามเครื่อง (ผ่าน socket) ก็ใช้แนวนี้
Shared memoryส่งข้อมูลจริงผ่าน memory ร่วมไม่ยุ่งกับ kernel ไม่ต้องสลับ mode จึง เร็วกว่า แต่ โปรแกรมเมอร์ต้อง sync เอง ไม่งั้นเกิด race condition

Signal คืออะไร

Signal = software interrupt ที่แจ้ง process ว่าเกิด event สถานการณ์ที่เกิด: Errors/Exceptions (หารด้วยศูนย์, index เกิน), External events (กด Ctrl+C), Notifications (child ทำงานเสร็จบอก parent), Alarms (หมดเวลาที่ตั้งไว้)

เมื่อ process ได้รับ signal มีทางเลือก 3 แบบ:

  1. Catch: เขียน handler เอง เทียบเท่า exception handling แบบ try/catch
  2. ทำตาม default action ของ OS: ไม่เขียนจัดการ OS สั่งยังไงก็ทำตาม
  3. Mask: บอก OS ให้หน่วง signal ประเภทนั้นไว้ (เช่นกำลังจัดการ signal อื่นอยู่) พอเสร็จค่อยปลด

ชื่อ signal ประกาศใน signal.h ขึ้นต้นด้วย SIG (ค่าจริงคือตัวเลข):

Signalเกิดเมื่อจัดการได้ไหม
SIGFPEคำนวณคณิตศาสตร์ผิดพลาด เช่น หารด้วย 0, overflow/underflowได้
SIGINTผู้ใช้กด Ctrl+C (คือ signal เบอร์ 2)ได้
SIGTERMขอให้อีก process จบการทำงาน (software termination)ได้ (เขียน handler หรือไม่สนใจก็ได้)
SIGQUITผู้ใช้กด Ctrl+\ บน terminalได้
SIGUSR1, SIGUSR2user-defined สำหรับแอปพลิเคชันได้
SIGKILLบังคับจบ process (เบอร์ 9)catch หรือ ignore ไม่ได้ ต้องทำตาม default คือต้องจบการทำงาน

signal() ใช้ลงทะเบียน ไม่ใช่ส่ง (คลิป 7.2.1)

จุดที่อาจารย์บอกว่านักเรียนสับสนมากที่สุด: signal() ไม่ใช่ฟังก์ชันส่ง signal แต่ใช้ ลงทะเบียนกับ OS ว่าเมื่อ signal นี้เกิด ให้ไปเรียกฟังก์ชันอะไร หรือขอไม่รับ (SIG_IGN)

  • signal(int signum, void (*handler)(int)): ตัวแรกคือหมายเลข signal (ใช้ค่าคงที่อย่าง SIGINT อย่าเขียนตัวเลขตรง ๆ) ตัวที่สองคือ pointer ไปยัง handler
  • Handler ต้อง รับ int 1 ตัว (signal number) และคืนค่า void เท่านั้น
#include <stdio.h>
#include <signal.h>

void inthandler(int);          /* handler ต้องเป็น void รับ int ตัวเดียว */

int main(void) {
    signal(SIGINT, inthandler);   /* ลงทะเบียน: SIGINT (Ctrl+C) ให้ไปเรียก inthandler */
    while (1) {                   /* ถ้า comment บรรทัด signal() ออก: Ctrl+C ครั้งเดียวโปรแกรมจบทันที (default) */
        printf("Running\n");
        sleep(1);
    }
}

void inthandler(int sig) {
    signal(SIGINT, SIG_IGN);      /* ระหว่างจัดการ ขอ ignore Ctrl+C ที่ส่งมาซ้ำ */
    printf("จะเลิกจริงหรอ? (y/n) ");
    if (ตอบ y) exit(0);           /* ตอบ y จบโปรแกรม */
    signal(SIGINT, inthandler);   /* ตอบอย่างอื่น: reinstall handler เดิมรับครั้งต่อไป */
}

จัดการหลาย signal ในโปรแกรมเดียวได้ 2 วิธี: ติดตั้ง handler ละ signal (แยกฟังก์ชัน) หรือ handler เดียว + switch(sig) เลือกใช้ตามความซับซ้อนของการจัดการแต่ละ signal

การส่ง Signal: raise() กับ kill() (คลิป 7.2.2)

int raise(int sig);         /* ส่ง signal ถึง process ตัวเอง: สำเร็จ return 0, error คืนค่าไม่ใช่ 0 */
int kill(pid_t pid, int sig);  /* ส่ง signal ถึง process อื่น: สำเร็จ return 0, ไม่สำเร็จ return -1 */
  • raise() ใช้เพื่อ ทดสอบว่าถ้าได้รับ signal แบบนี้ โปรแกรมจะตอบสนองถูกต้องไหม ถ้ามี handler ลงทะเบียนไว้ก็ไปทำ handler ไม่มีก็ทำ default ตัวอย่างคลิป: loop คำนวณ factorial ถ้าค่าใหม่น้อยกว่าค่าเก่า (overflow วนกลับ) ก็ raise(SIGUSR1) ให้ handler รายงานค่าสูงสุด เครื่องอาจารย์เก็บได้ถึง 20!
  • kill(pid, sig) ความหมายของ pid: pid > 0 = process ที่มี PID นั้น; pid = 0 = ทุก process ใน process group เดียวกับผู้เรียก; pid = -1 = ทุก process ที่ผู้เรียกมีสิทธิ์ ยกเว้น process 1 (init); pid < 0 (อื่น ๆ) = ทุก process ที่ process group ID = |pid|
/* ตัวอย่างแม่-ลูกของอาจารย์: ลูกลงทะเบียนจับ SIGTERM คนเดียว แม่เป็นคนส่ง */
/* ฝั่งลูก (fork คืนค่า 0) */
signal(SIGTERM, sig_handler);    /* ลูกพิมพ์ข้อความลาก่อนเมื่อถูกแม่ส่ง SIGTERM มา */
printf("ลูก pid=%d, แม่ pid=%d\n", getpid(), getppid());
while (1) { sleep(1); }

/* ฝั่งแม่ */
sleep(3);                        /* ให้ลูกมีชีวิตสัก 3 วินาที */
printf("แม่จะฆ่าลูกเบอร์ %d\n", pid);   /* pid ได้จากค่า return ของ fork() */
kill(pid, SIGTERM);              /* ส่ง SIGTERM ไปฆ่าลูก */
wait();
printf("ฉันฆ่าลูกคนนี้แล้ว\n");

คำสั่ง kill บน shell

  • รูปแบบ kill -SIGNAL PID ส่งให้หลาย process พร้อมกันได้ ระบุ signal เป็นเลขหรือชื่อก็ได้ (ชื่อ ไม่ต้องมี SIG นำหน้า เช่น kill -INT 29769)
  • ถ้าไม่ระบุ signal → default คือ SIGTERM (ชื่อโปรแกรม kill มาจากจุดนี้)
  • kill -9 pid = SIGKILL สำหรับ process ดื้อ: แม้เขียน handler ดัก SIGTERM ไว้ kill -TERM ก็ไม่มีผล ต้องใช้ -9 และพยายามดัก SIGKILL ก็เสียเปล่า
  • การใช้จริงที่อาจารย์ย้ำ: บน server ถ้า process เราค้าง ให้ ps -a หา PID แล้ว kill -9 (แอดมินไม่ reboot ให้แน่ เพราะคนอื่นเดือดร้อนด้วย)

Message Passing: blocking vs non-blocking

  • สื่อสารด้วย send(message) / receive(message) โดยต้องสร้าง communication link ก่อน (write = send, read = receive ก็ได้)
  • Blocking (synchronous): blocking send = sender block จน message ถูกรับ; blocking receive = receiver block จนมี message
  • Non-blocking (asynchronous): send แล้วทำงานต่อ; receive ได้ message หรือ null กลับไปทำอย่างอื่น วิชานี้เน้น blocking อย่างเดียว (เป็น default)
  • เพราะ OS เป็นคนดูแล message passing จึงจัดจังหวะให้ เช่นถ้า message box เต็มและคนรับยังไม่อ่าน OS จะไม่ให้เขียนทับ
มักออกสอบ
  • 3 โมเดล IPC + เหตุผลของ cooperating processes 3 ข้อ
  • trade-off หัวใจของคลิป: message passing ช้า (สลับ mode) แต่ OS sync ให้ / shared memory เร็ว แต่โปรแกรมเมอร์ sync เอง ไม่งั้น race condition
  • signal คือ software interrupt, 3 วิธีจัดการ signal (catch/default/mask), SIGKILL พิเศษอย่างไร
  • signal() คือฟังก์ชันลงทะเบียน handler ไม่ใช่ส่ง, handler ต้อง void รับ int, SIG_IGN กัน signal ซ้ำ
  • raise() กับ kill() ต่างกันอย่างไร, ความหมาย pid 0 / -1 ใน kill(), kill -9, default ของคำสั่ง kill = SIGTERM
  • blocking vs non-blocking send/receive (default คือ blocking)

Pipe และ Shared Memory

Pipe (anonymous pipe)

Pipe = implementation ของ message passing ที่นิยม: ท่อสื่อสาร ทางเดียว (one-way) แบบ stream of bytes เป็นพื้นที่ memory ที่ OS ปกป้องไว้ใช้เป็น buffer แบ่งเป็น 2 ประเภท วิชานี้เรียนเฉพาะ unnamed:

  • Unnamed pipe: พื้นที่ชั่วคราว ใช้ระหว่าง process ที่มีความสัมพันธ์กัน (แม่-ลูก) พอ process จบ พื้นที่ถูกเอาคืน
  • Named pipe (FIFO): ให้ process ที่ไม่เกี่ยวข้องกันคุยกันได้โดยใช้คอนเซปต์ไฟล์ พิเศษตรงที่อ่านแล้ว ข้อมูลถูกลบออกจากไฟล์ กันได้รับซ้ำ

File descriptor และฟังก์ชัน pipe() (คลิป 8.1.1)

File descriptor = ตัวเลขใช้แทนไฟล์ที่กำลังทำงานด้วย โดย OS มองอุปกรณ์เป็นไฟล์หมดจึงมี fd มาตรฐานถูกใช้ไป 3 ตัว: 0 = stdin (คีย์บอร์ด), 1 = stdout (จอ), 2 = stderr (จอ) → fd ใหม่เริ่มจากเบอร์ 3 ขึ้นไป

int pfd[2];
pipe(pfd);   /* สร้างท่อสื่อสารแบบทิศทางเดียว: pfd[0] = ปลายอ่าน (read end),
                pfd[1] = ปลายเขียน (write end), สร้างไม่สำเร็จ return -1 */

write(pfd[1], buff, size);   /* ปลายเขียน, buffer, จำนวนไบต์ (เขียนไม่ครบ buffer ก็ได้) */
read(pfd[0], buff, SIZE);    /* ปลายอ่าน, ตัวแปรเก็บ, ขนาดสูงสุดต่อรอบ
                                ข้อมูลใหญ่กว่า buffer ต้องอ่านหลายรอบ, read คืนจำนวนไบต์ที่อ่านได้จริง */
  • read/write เป็น blocking: ฝั่งอ่านจะ block รอจนมีข้อมูล อาจารย์สาธิตด้วยการให้แม่ sleep(2) ก่อนเขียน ลูกเข้ามา read ก่อนก็ต้องรอ
  • แม่ต้องสร้าง pipe ก่อนแล้วค่อย fork() เพราะหลัง fork ลูกได้ file descriptor ชุดเดียวกับแม่ จึงเห็นปลายทั้งสองของท่อเดียวกัน
  • หลัง fork จะมี read end 2 ตัว + write end 2 ตัว เพื่อความชัดเจน ฝั่งส่งต้องปิด read end, ฝั่งรับปิด write end
#define SIZE 1024              /* จริง ๆ ส่งได้ 1023 เผื่อที่ '\0' */
char buff[SIZE];
char buffread[5 + 1];          /* ฝั่งรับอ่านครั้งละ 5 ไบต์ +1 เผื่อ '\0' ปิดท้าย */
int pfd[2], nread, pid;        /* nread = จำนวนไบต์ที่ read อ่านได้ในแต่ละรอบ */

if (pipe(pfd) == -1) { /* สร้าง pipe แล้วตรวจ error */ }

pid = fork();
if (pid == 0) {                      /* ลูก = คนอ่าน */
    close(pfd[1]);                   /* ปิดปลายเขียนที่ไม่ใช้ */
    while ((nread = read(pfd[0], buffread, 5)) != 0) {
        printf("%s", buffread);      /* อ่านทีละ 5 ไบต์พิมพ์ไปเรื่อย ๆ จนหมด */
    }
    close(pfd[0]);                   /* ปิดปลายอ่านตัวเอง = จบการใช้ pipe */
} else {                             /* แม่ = คนเขียน */
    close(pfd[0]);                   /* ปิดปลายอ่านที่ไม่ใช้ */
    sleep(2);                        /* ตั้งใจให้ลูก block รอ จนกว่าแม่เขียนเสร็จ */
    write(pfd[1], buff, strlen(buff) + 1);  /* +1 เพื่อส่ง '\0' ปิดท้ายไปด้วย (strlen ไม่นับ '\0') */
    close(pfd[1]);
    wait();                          /* รอให้ลูกอ่านจนจบ */
}
ข้อผิดพลาดที่พบบ่อย
  • กับดัก '\0' ที่อาจารย์สาธิต: ถ้าเขียนแค่ strlen(buff) ไม่บวก 1 ทุกอย่างทำงานปกติ แต่ ตัวสุดท้ายจะมีตัวอักษรขยะโผล่มา เป็นเศษสตริงเก่าค้างใน buffer เพราะฟังก์ชัน string ใน C ส่วนใหญ่เช็ค '\0'
  • ลืมปิดปลาย pipe ที่ไม่ใช้หลัง fork และลืมว่า pipe ต้องสร้าง ก่อน fork
  • pipe 1 อัน = ทางเดียวเท่านั้น ถ้าจะให้แม่เขียนหาลูกแล้วลูกตอบกลับ ต้องสร้าง pipe 2 อัน (ตัวอย่าง two_pipes.c ให้ไปรันเอง)

dup2 และกลไกของ ls | wc (คลิป 8.1.2)

wc นับ 3 อย่าง: จำนวนบรรทัดใหม่ (newline), จำนวนคำ, จำนวนอักขระ ทดลองกับโฟลเดอร์ 4 ไฟล์ ls | wc ได้ 4 newline, 4 คำ, 29 อักขระ อยากได้แค่จำนวนไฟล์ใช้ ls | wc -l ข้อควรระวัง: ชื่อไฟล์มีช่องว่างจะนับคำเพี้ยน ให้ดูที่ newline (-l)

กลไก: ls เขียนที่ fd 1 (stdout) ปกติ, wc อ่านที่ fd 0 (stdin) ปกติ พอสร้าง pipe จะได้ fd ใหม่ เช่น 3 (เขียน) กับ 4 (อ่าน) จึงต้องจับคู่ให้ถูกด้วย dup2 (dup + "to"):

dup2(pfd[1], 1);   /* พารามิเตอร์แรก = fd ต้นฉบับ, ตัวที่สอง = fd ปลายทาง
                      "3 อยากเป็น 1" → จากนี้เขียนลง fd 1 = เขียนลง pipe */
dup2(pfd[0], 0);   /* "4 อยากเป็น 0" → จากนี้อ่านจาก fd 0 = อ่านจาก pipe */

pipe(pfd);
pid = fork();
if (pid == 0) {              /* ลูก = ls (ฝั่งเขียน) */
    close(pfd[0]);           /* ปิดปลายอ่านที่ไม่ใช้ */
    dup2(pfd[1], 1);         /* ดันปลายเขียนไปแทน stdout (1) */
    close(pfd[1]);           /* ปิด fd ต้นฉบับของ pipe */
    execl("/bin/ls", "ls", NULL);   /* ผลลัพธ์ไหลเข้า pipe แทนจอ */
    perror("execl");
} else {                     /* แม่ = wc (ฝั่งอ่าน) */
    close(pfd[1]);           /* ปิดปลายเขียนที่ไม่ใช้ */
    dup2(pfd[0], 0);         /* ดันปลายอ่านไปแทน stdin (0) */
    close(pfd[0]);
    execl("/usr/bin/wc", "wc", NULL);
}

ผลลัพธ์เหมือนพิมพ์ ls | wc ตรง ๆ และ dup2 ใช้ redirect file descriptor อย่างอื่นได้ด้วย เช่นย้าย stdout ไปไฟล์

Shared Memory: แนวคิด

Shared memory = พื้นที่ memory ที่ attach อยู่ใน address space ของหลาย process พร้อมกัน ใช้เหมือน memory ของตัวเอง (process ไม่รู้ตัวว่าใช้พื้นที่แชร์) จุดสำคัญ 2 ข้อที่อาจารย์ย้ำทุกคลิป:

  • ไม่มี protection ไม่มีกลไกพิเศษกัน ใครรู้วิธีเข้าถึงก็ใช้ได้
  • OS ไม่ดูแล synchronization ให้ เป็นหน้าที่โปรแกรมเมอร์ ไม่จัดจังหวะกันเองจะเกิด race condition
  • ผู้ขอสร้าง (ใช้ key) เรียก server, ที่เหลือเรียก client และ server ต้องรันก่อน client เสมอ
#include <sys/types.h>   /* นิยาม type key_t */
#include <sys/ipc.h>
#include <sys/shm.h>

  • 1) ใส่เลขตรง ๆ (เช่น 1234): ง่ายแต่ ไม่ควรทำ คนอื่นนึกเลขเดียวกันได้ กลายเป็นใช้ shared memory ร่วมกันโดยไม่เกี่ยวข้องกัน "ยุ่งแน่ ๆ"

(โฟลเดอร์ปัจจุบัน) เพราะแต่ละ user รันใน home ของตัวเองที่ไม่ซ้ำ id ใช้แยกหลายโปรแกรมใน path เดียวกัน แต่ ไม่การันตี 100% ถ้าใครจงใจรู้ path/id ก็ยังเข้าถึงได้ และ server กับ client ต้องรันจากโฟลเดอร์เดียวกัน

ฟังก์ชันหน้าที่รายละเอียดที่อาจารย์เน้น
shmget(key, size, flag)ขอสร้าง/ขอเข้าใช้server ใช้ flag IPC_CREAT | 0666 (สร้าง + สิทธิอ่านเขียนทุกคน), client ใช้ของที่ server สร้างแล้ว size กับ flag ใส่ 0 ได้, สำเร็จคืน shared memory ID ไม่สำเร็จคืนค่าลบ มี IPC_EXCL (กันสร้างซ้ำ) แต่วิชานี้ไม่ใช้
shmat(shmid, shmaddr, flag)attach เข้า address space ตัวเองปกติ shmaddr = NULL (ให้ OS เลือกจุดเชื่อม), flag = 0 (อ่านเขียน) หรือ SHM_RDONLY, คืน pointer แบบ void * ต้อง cast เป็นชนิดข้อมูลที่เก็บ, ล้มเหลวคืน -1
shmdt(shm_ptr)detach ถอนตัวไม่ได้ลบ shared memory ถอนแล้วอยากกลับมาใช้เรียก shmat ใหม่ได้, สำเร็จคืน 0
shmctl(shm_id, IPC_RMID, NULL)ควบคุม และในวิชานี้ใช้เพื่อ ลบลบแล้วใช้ใหม่ต้อง shmget + shmat ใหม่ การลบเป็นหน้าที่ของ server เท่านั้น client ห้ามลบ

0666 เป็นเลขฐาน 8 เลียนแบบสิทธิไฟล์ Unix: 9 บิตแบ่ง 3 กลุ่ม (owner / group / others) กลุ่มละ 3 บิต rwx เช่น rwx r-x r-x = 111 101 101 = 755, 666 = rw- rw- rw- อ่าน+เขียนทุกกลุ่ม ใช้ chmod เปลี่ยนสิทธิได้ เช่น chmod 0664 temp (ใส่ 0 นำหน้าเพื่อบอกว่าเป็นฐาน 8)

โค้ดตัวอย่าง 1: แม่-ลูก (คลิป 8.2.3)

ผู้ใช้ป้อนเลข 4 ตัว แม่รับไปใส่ shared memory แล้ว fork ให้ลูกอ่านมาพิมพ์

int shmid;
int *ptr;      /* เก็บข้อมูลชนิดไหน ประกาศ pointer เป็นชนิดนั้น */

shmid = shmget(IPC_PRIVATE,            /* แม่ลูกคุยกัน ใช้คีย์ unique ได้เลย */
               4 * sizeof(int),        /* จองพื้นที่เก็บ integer 4 ตัว */
               IPC_CREAT | 0666);      /* สร้างใหม่ + สิทธิอ่านเขียนกับใครก็ได้ */
if (shmid < 0) exit(1);                /* เช็ค error ทุกขั้น */

ptr = (int *) shmat(shmid, NULL, 0);   /* attach, อย่าลืม casting ให้ตรงชนิด */
if (ptr == (int *) -1) exit(1);
/* แม่ใส่เลข 4 ตัวลง ptr[0..3] แล้ว fork: ลูกได้รับทุกอย่างจากแม่ (inherit)
   จึงไม่ต้อง shmget ซ้ำ อ่านค่า พิมพ์ แล้ว exit, แม่ wait รอลูก */
shmdt(ptr);                     /* แม่ถอนตัว */
shmctl(shmid, IPC_RMID, NULL);  /* แม่ (ฝั่ง server) ลบ shared memory */

โค้ดตัวอย่าง 2: server-client เก็บ struct พร้อมจัดจังหวะเอง (คลิป 8.2.3)

struct shared_memory {
    int status;      /* NOT_READY = -1, FILLED = 0, TAKEN = 1  ใช้ประสานจังหวะ */
    int data[4];     /* เลข 4 ตัว */
};
struct shared_memory *shm_ptr;

key = ftok(".", 'x');   /* ทั้งคู่ต้องใช้ path กับ id เดียวกัน = รันจากโฟลเดอร์เดียวกัน */

/* -------- Server (รันก่อนเสมอ) -------- */
shmid = shmget(key, sizeof(struct shared_memory), IPC_CREAT | 0666);
shm_ptr = (struct shared_memory *) shmat(shmid, NULL, 0);
shm_ptr->status = NOT_READY;     /* ตั้งก่อน เพื่อให้ใส่เลขเสร็จก่อน client อ่าน */
/* ใส่เลข 4 ตัวลง data */
shm_ptr->status = FILLED;        /* บอก client ว่าอ่านได้แล้ว */
while (shm_ptr->status != TAKEN);/* รอ client อ่านเสร็จ */
shmdt(shm_ptr);
shmctl(shmid, IPC_RMID, NULL);   /* server คนเดียวที่ลบ */

/* -------- Client -------- */
shmid = shmget(key, 0, 0666);    /* size ใส่ 0 ได้ เพราะ server สร้างไว้แล้ว */
shm_ptr = (struct shared_memory *) shmat(shmid, NULL, 0);
while (shm_ptr->status != FILLED);  /* รอจน server ใส่ครบ */
/* อ่านข้อมูล */
shm_ptr->status = TAKEN;         /* ตอบกลับว่าอ่านแล้ว */
shmdt(shm_ptr);
ข้อผิดพลาดที่พบบ่อย
  • การจัดจังหวะด้วย status flag ของโปรแกรมเมอร์ ยังไม่สมบูรณ์ อาจารย์สาธิตให้ server sleep 10 วินาทีก่อนเซ็ต status → client เข้ามาเช็คก่อน เจอค่า 0 ซึ่งบังเอิญตรงกับ FILLED = 0 (memory ให้ค่าเริ่มต้น 0) จึงหลุด loop ไปอ่านข้อมูลว่าง ๆ
  • เปลี่ยน FILLED เป็น -99 ก็แก้แค่ชั่วคราว compiler อื่นอาจให้ค่าขยะ สักวันอาจบังเอิญเท่ากันอีก ทางแก้ที่ดีคือใช้กลไก synchronization ของ OS (ดู หัวข้อถัดไป)
มักออกสอบ
  • pipe เป็น one-way stream of bytes: เขียนผ่าน pfd[1] อ่านผ่าน pfd[0], ต่าง unnamed กับ named pipe (FIFO)
  • fd 0/1/2 คืออะไร, pipe ต้องสร้างก่อน fork, ต้องปิดปลายที่ไม่ใช้ทั้งสองฝั่ง, read ต้องอ่านหลายรอบเมื่อข้อมูลใหญ่
  • กับดัก '\0': เขียน strlen(buff)+1 เพื่อส่งตัวปิดสตริงไปด้วย
  • dup2(src, dst) ใช้ทำอะไร, กลไก ls | wc ทั้งเส้น (close → dup2 → close → exec), สื่อสารสองทางต้องใช้ 2 pipes
  • ลำดับชีวิต shared memory: shmget → shmat → ใช้งาน → shmdt → shmctl, shmdt ต่างจาก shmctl อย่างไร, ทำไม client ลบไม่ได้
  • 3 วิธีสร้าง key + ข้อจำกัดของแต่ละแบบ, ความหมาย flag IPC_CREAT | 0666, 0666 เป็นเลขฐาน 8 อย่างไร
  • ทำไม shared memory ต้องมี synchronization (ไม่มี protection + OS ไม่ sync ให้)

Process Synchronization

Bounded Buffer: จุดตั้งต้นของปัญหา (คลิป 9.1)

Producer เขียนข้อมูลลง buffer, Consumer อ่านจาก buffer ถ้าไม่จัดจังหวะเกิด 2 กรณี: ข้อมูลหาย (producer เขียนครบ 5 ช่องแล้ววนกลับเขียน F ทับ A ก่อน consumer อ่าน) และ อ่านข้อมูลซ้ำ (consumer อ่านครบแล้ววนกลับไปอ่านข้อมูลเดิมอีก)

#define BUFFER_SIZE 5
int count = 0;          /* shared: จำนวนข้อมูลใน buffer ที่ยังไม่ถูกอ่าน */
int in = 0, out = 0;    /* in เป็นของ producer เท่านั้น, out เป็นของ consumer เท่านั้น */

/* ---- Producer ---- */
while (count == BUFFER_SIZE);   /* buffer เต็ม ติด loop รอ */
buffer[in] = item;
in = (in + 1) % BUFFER_SIZE;    /* วนกลับช่องแรกเมื่อถึงช่องสุดท้าย */
count++;

/* ---- Consumer ---- */
while (count == 0);             /* ไม่มีข้อมูล ติด loop รอ */
item = buffer[out];
out = (out + 1) % BUFFER_SIZE;
count--;

ใช้ count เป็นตัวจัดจังหวะได้ไหม? อาจารย์ตอบว่า ยังไม่สมบูรณ์ 100% เพราะถูกต้องก็ต่อเมื่อ producer ทำ count++ จนจบโดยไม่ถูกขัด แต่ OS ขัดจังหวะเมื่อไหร่ก็ได้ สาเหตุอยู่ที่ว่า count++ ไม่ใช่คำสั่งเดียว (ดูหัวข้อ race condition)

Race Condition (คลิป 9.2)

Race condition = หลาย process เข้าไปแก้ shared data พร้อมกันแล้ว ผลลัพธ์ขึ้นกับลำดับการทำงาน (ผลเป็นของ process ที่เสร็จทีหลังและเป็นค่าที่ผิด) เพราะ count++ และ count-- จริง ๆ ถูกแตกเป็น 3 คำสั่งระดับเครื่อง:

count++                          count--
1) register1 = count             1) register2 = count    (โหลดจาก memory)
2) register1 = register1 + 1     2) register2 = register2 - 1
3) count = register1             3) count = register2    (เขียนคืน memory)
ตัวอย่าง interleaving จากสไลด์ (S0-S5): count เริ่ม 5, producer +1 และ consumer -1 คำตอบที่ถูกคือ 5
  1. S0: producer register1 = count → register1 = 5
  2. S1: producer register1 = register1 + 1 → register1 = 6
  3. S2: consumer register2 = count → register2 = 5 (count ยังเป็น 5 เพราะ producer ยังไม่เขียนคืน)
  4. S3: consumer register2 = register2 - 1 → register2 = 4
  5. S4: producer count = register1 → count = 6
  6. S5: consumer count = register2 → count = 4 (ผิด! ที่ถูกคือ 5)

สลับลำดับก็อาจได้ 6 ซึ่งก็ผิด ต่อให้รันได้เป็นเดือนเป็นปีโดยไม่มีปัญหา พอสักวันเกิดขึ้นก็ไล่โปรแกรมตาเหลือกว่าจะเจอ ทางแก้คือ synchronization = การล็อก: ใครใช้ shared data ให้ล็อกไว้ ถูกขัดกลางทางก็ยังล็อกอยู่ คนอื่นเข้ามาทำอะไรไม่ได้ (แต่ถ้าล็อกไม่ดีจะเกิด deadlock ดู หัวข้อ Deadlock)

Critical-Section Problem

Critical section (critical region) = ส่วนของโปรแกรมที่ต้องรันให้จบก่อน จึงจะให้ process อื่นเข้าใช้ resource นั้นได้ เช่น count++ ของ producer กับ count-- ของ consumer อัลกอริทึมแก้ปัญหาต้องผ่าน 3 เงื่อนไข (อาจารย์เปรียบเทียบเป็นห้องน้ำ 1 ห้อง):

  1. Mutual Exclusion: ณ เวลาใดเวลาหนึ่งมีเพียง process เดียวอยู่ใน critical section (ติดกลอนห้องน้ำ ใครเข้าก็ล็อก)
  2. Progress: ถ้าไม่มีใครอยู่ใน critical section และมีคนขอเข้า ต้องเลือกจาก process ที่อยากใช้เท่านั้น อย่ายุ่งกับคนที่ไม่อยากใช้ ตัวอย่างไม่ผ่าน: กำหนดคิวตายตัวแดง→เขียว→เหลือง พอแดงไม่อยากเข้า เขียวก็เข้าไม่ได้ตลอดทั้งที่ห้องว่าง
  3. Bounded Waiting: มีขอบเขตจำนวนครั้งที่ process อื่นเข้า critical section ได้หลังจาก process หนึ่ง request ไปแล้ว ตัวอย่างไม่ผ่าน: แดงใช้เสร็จออกมาก็แซงคิวเข้าใหม่ทันที เขียวกับเหลืองไม่รู้จะได้เมื่อไหร่

ข้อเท็จจริงจากคลิป: ถ้าเลือกได้ข้อเดียวที่ต้องผ่านคือ ข้อ 1 และถ้าไม่ผ่านข้อ 2 ก็จะไม่ผ่านข้อ 3 ด้วย (สมมติฐานของโจทย์: ทุก process รันด้วย speed ไม่เป็นศูนย์ ไม่สันนิษฐาน relative speed)

Peterson's Solution (2 process) และ Bakery Algorithm (n process)

Peterson ใช้ได้กับ 2 process แต่ครบทั้ง 3 ข้อ สมมติว่า LOAD และ STORE เป็น atomic ตัวแปร shared: int turn (ตาของใครเข้า) และ boolean flag[2] (พร้อมเข้าหรือยัง)

/* โค้ดของ Pi */
do {
    flag[i] = TRUE;          /* ประกาศว่าพร้อมเข้า */
    turn = j;                /* ยกตาให้อีกฝ่ายก่อน */
    while (flag[j] && turn == j);   /* รอจนอีกฝ่ายไม่พร้อม หรือตาเป็นของเรา */
    /* critical section */
    flag[i] = FALSE;
    /* remainder section */
} while (1);

Bakery Algorithm แก้ได้กับ n process ด้วยแนวคิด กดบัตรคิวเหมือนไปธนาคาร: เจ้าของเลขน้อยสุดเข้าก่อน เลขเท่ากันใช้ process id ตัดสิน (Pi ก่อน Pj เมื่อ i < j) ใช้ notation lexicographical order (ticket #, process id #) shared data: boolean choosing[n], int number[n] (เริ่ม false/0)

choosing[i] = true;                 /* กำลังกดบัตร */
number[i] = max(number[0], ..., number[n-1]) + 1;   /* ได้เลขมากสุด + 1 */
choosing[i] = false;
for (j = 0; j < n; j++) {           /* รอจนไม่มีใครกดบัตรอยู่
    while (choosing[j]);                และไม่มี (number[j], j) < (number[i], i) */
    while ((number[j] != 0) && ((number[j], j) < (number[i], i)));
}
/* critical section */
number[i] = 0;                      /* เสร็จแล้วเคลียร์บัตร */

อาจารย์วิเคราะห์ว่า Bakery ผ่าน 3 ข้อ: mutual exclusion (เลขน้อยเข้าก่อน เลขซ้ำดู PID), progress (ต้องมากดบัตรถึงจะถูกพิจารณา), bounded waiting (ใช้เสร็จต้องออกมากดบัตรใหม่ บัตรใหม่ไม่มีทางน้อยกว่าคนรออยู่) แต่ทั้ง Peterson และ Bakery ยังเหลือปัญหา busy waiting อยู่

Semaphore (คลิป 10.1)

Semaphore S = ตัวแปร integer เข้าถึงได้ผ่าน 2 atomic operations เท่านั้น: wait() และ signal() (เดิมชื่อ P() และ V()) OS รับประกันว่าได้ทำแล้วต้องได้ทำจนจบ ไม่ถูกขัดจังหวะ ระวังสับสน: ไม่ใช่ wait() ที่แม่รอลูก และไม่ใช่ signal ของหัวข้อ IPC

wait(S) {            /* เดิมชื่อ P */
    while (S <= 0);  /* ค่า S <= 0 → ติด loop รอ (busy waiting) */
    S--;             /* ผ่าน → ลดค่า S แล้วทำงานต่อ */
}
signal(S) {          /* เดิมชื่อ V */
    S++;
}

Busy waiting คือ process ที่ไม่ผ่านเงื่อนไขจะติด while loop พอ OS เลือกมันเข้ามาทำงานก็ทำอะไรไม่ได้ เสีย time quantum ทั้งที่ไม่พร้อม อุปมาของอาจารย์: บ้านชั้นบนอยากใช้ห้องน้ำชั้นล่าง จึงวางโหลใส่หินไว้หน้าบันได (หิน = ค่า S): มีหิน (S > 0) หยิบหิน (wait: S--) แล้วลงไปใช้, ใช้เสร็จเอาหินคืนโหล (signal: S++) คนรอเห็นหินก็ได้เข้า ห้องน้ำ 2 ห้องก็ใส่หิน 2 ลูก

  • Counting semaphore: ค่าไม่จำกัดช่วง (ทรัพยากรหลายหน่วย)
  • Binary semaphore: ค่าได้แค่ 0 กับ 1 เรียกอีกอย่าง mutex lock
  • ใช้คุม critical section ด้วย binary semaphore: ตั้ง S = 1 → wait(S) → critical section → signal(S)

Implementation แบบ ไม่มี busy waiting: แต่ละ semaphore มี waiting queue (เก็บ value + pointer) และคำสั่ง block (หย่อน process ลง waiting queue) กับ wakeup (ดึง process หนึ่งกลับ ready queue)

wait(S) {
    S--;
    if (S < 0) { add this process to waiting queue; block(); }
}
signal(S) {
    S++;
    if (S <= 0) { remove a process P from waiting queue; wakeup(P); }
}
  • เงื่อนไขจำไว้: value < 0 ใน wait กับ value <= 0 ใน signal (ยังติดลบแปลว่ามีคนรออยู่ จึงปลุก 1 ตัว)
  • วิเคราะห์ 3 เงื่อนไข: mutual exclusion ผ่านแน่, progress ผ่าน, bounded waiting ขึ้นกับ implementation ของ wakeup ถ้าปลุก "ใครก็ได้" ไม่ผ่าน ถ้า implement แบบ FIFO ผ่าน

Classical Problems of Synchronization (คลิป 10.2)

1) Bounded-Buffer Problem: N buffer (ละ 1 item) ใช้ semaphore 3 ตัวแทนตัวแปร count: mutex = 1, full = 0, empty = N

semaphore mutex = 1;  /* binary: ล็อก buffer */
semaphore full  = 0;  /* counting: จำนวนช่องที่มีข้อมูล */
semaphore empty = n;  /* counting: จำนวนช่องว่าง = ขนาด buffer */

/* ---- Producer ---- */
wait(empty);      /* เช็คมีช่องว่างไหม → หยิบหินจากโหล empty */
wait(mutex);      /* ล็อก buffer (ห้าม consumer อ่านขณะเขียน) */
/* ใส่ item */
signal(mutex);    /* ปลดล็อก */
signal(full);     /* ย้ายหินไปใส่โหล full = แจ้งว่ามีข้อมูลใหม่ */

/* ---- Consumer ---- */
wait(full);       /* เช็คมีข้อมูลไหม → หยิบหินจากโหล full */
wait(mutex);      /* ล็อก buffer (ห้าม producer เขียนขณะอ่าน) */
/* ดึง item */
signal(mutex);
signal(empty);    /* คืนหินโหล empty = แจ้งว่ามีช่องว่าง */

จุดน่าสังเกต: producer ไม่เคย wait(full) แต่ signal(full) เพราะมันย้ายหินจากโหล empty ไปใส่โหล full เพื่อส่งสัญญาณว่ามีข้อมูลใหม่ (consumer ทำกลับกัน) อาจารย์ตอบว่า "รู้ได้ยังไงต้องทำแบบนี้" คือขึ้นอยู่กับแอปพลิเคชัน โปรแกรมเมอร์ต้องคิดเอง

2) Readers-Writers Problem: Readers อ่านอย่างเดียว, Writers อ่าน+เขียน อนุญาต readers หลายตัวพร้อมกัน แต่ writer ได้ตัวเดียว และ writer ทำงานอยู่ห้ามใครยุ่ง shared data: mutex = 1, wrt = 1, readcount = 0

/* ---- Writer ---- */
wait(wrt);        /* มีหิน = ยังไม่มีใครใช้ data → ล็อก */
/*  writing  */
signal(wrt);

/* ---- Reader ---- */
wait(mutex);              /* ล็อกช่วงอัปเดต readcount */
readcount++;
if (readcount == 1) wait(wrt);   /* reader ตัวแรกล็อก data กัน writer */
signal(mutex);
/*  reading  */
wait(mutex);
readcount--;
if (readcount == 0) signal(wrt); /* reader ตัวสุดท้ายปลดล็อกให้ writer */
signal(mutex);

ประเด็นสำคัญ: reader ตัวแรกเป็นคนล็อก data และ reader ตัวสุดท้ายเป็นคนปลดล็อก ตราบใดที่ยังมี reader อยู่ writer เขียนไม่ได้เลย

3) Dining-Philosophers Problem: นักปราชญ์ 5 คน ชีวิตมีแค่คิดกับกิน มีตะเกียบ 5 ข้าง (ไม่ใช่ 5 คู่) กินต้องได้ทั้งซ้ายและขวา เชื่อมกับ OS: นักปราชญ์ = process, ตะเกียบ = ทรัพยากร ใช้ chopstick[5] แต่ละอัน init = 1

semaphore chopstick[5];            /* binary sem ทุกตัวเริ่มต้น = 1 */

/* นักปราชญ์คนที่ i */
do {
    /* คิดปรัชญา พอหิว: */
    wait(chopstick[i]);              /* หยิบตะเกียบซ้าย: ว่าง → ถือ, มีคนถือ → รอ */
    wait(chopstick[(i + 1) % 5]);    /* หยิบตะเกียบขวา: ระหว่างรอไม่วางซ้ายลง */
    /*  กินข้าว  */
    signal(chopstick[i]);            /* วางซ้าย แจ้งเพื่อนบ้านว่าว่างแล้ว */
    signal(chopstick[(i + 1) % 5]);  /* วางขวา */
} while (1);

ปัญหาของทางแก้นี้คือ deadlock: สมมติทุกคนหิวพร้อมกันแล้วหยิบตะเกียบซ้ายพร้อมกัน ตะเกียบ 5 ข้างอยู่ในมือหมด ทุกคนรอตะเกียบขวา แต่จะมีใครวางตะเกียบได้ต้องกินก่อน ทั้งที่ไม่มีใครได้กิน → "ตายทั้งโต๊ะ"

ข้อผิดพลาดที่พบบ่อย
  • ปัญหาไม่ได้เกิดจากตัว semaphore แต่เกิดจากโปรแกรมเมอร์ เพราะ semaphore เป็นกลไกระดับต่ำ ไม่มีฟีเจอร์ของ OS หรือภาษามาเช็คให้ รู้ตัวตอนผลลัพธ์ผิดเท่านั้น
  • ข้อผิดพลาดคลาสสิก: ใช้ signal(mutex) ... wait(mutex) (สลับลำดับ: เหมือนเติมหิน "อะไรก็ไม่รู้" ลงโหลที่ควรมีหินลูกเดียว), wait(mutex) ... wait(mutex) (deadlock), ลืม wait หรือ signal หรือทั้งคู่

การเขียนโปรแกรม Semaphore จริง (คลิป 10.3)

ใช้ POSIX semaphore ป้องกัน race condition ของตัวแปร counter ระหว่าง 2 เทรด

#include <semaphore.h>
#include <pthread.h>

int count = 5;      /* global: ใช้ร่วมกันระหว่างเทรด */
sem_t mutex;        /* binary semaphore คุมการอัปเดต count */

void *increment(void *arg) {
    sem_wait(&mutex);        /* sem_wait = wait (P) */
    int temp = count;        /* แตกเป็น 3 สเต็ป + sleep สุ่ม จำลองการถูกขัดจังหวะ */
    temp++;
    count = temp;
    sem_post(&mutex);        /* sem_post = signal (V) */
}
/* decrement เขียนโครงเดียวกัน แต่เป็น temp-- */

int main() {
    pthread_t t1, t2;
    sem_init(&mutex, 0, 1);  /* 1 = ค่าเริ่มต้นของ semaphore (ไม่ใช่ 0),
                                0 = แชร์เฉพาะเทรดใน process นี้ (ค่าอื่น = แชร์ข้าม process) */
    pthread_create(&t1, NULL, increment, NULL);
    pthread_create(&t2, NULL, decrement, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("%d\n", count);   /* ถูกต้องต้องได้ 5 */
    sem_destroy(&mutex);
}
  • Compile ต้องลิงก์ library: gcc program.c -lpthread รันแล้วได้ 5 ถูกต้อง
  • ทดลองปิด semaphore (comment out sem_wait/sem_post): ได้ 6 ซึ่งผิด จริง ๆ อาจเป็น 6, 4 หรือแม้แต่ 5 (ฟลุ๊คถูก) แล้วแต่ถูกขัดตรงไหน
  • macOS ไม่ support unnamed semaphore ต้องใช้ named semaphore: sem_open("ชื่อsem", O_CREAT, 0666, 1) แทน sem_init, sem_close + sem_unlink แทน sem_destroy ส่วน increment/decrement ไม่ต้องแก้

Monitor (คลิป 11.1)

Monitor = high-level abstraction สำหรับ synchronization อยู่ระดับสูงกว่า semaphore โครงสร้างคล้าย object ใน OOP: รวม shared variables + procedures + initialization code ไว้ในก้อนเดียว และ มี process ทำงานใน monitor ได้ครั้งละ 1 จึงได้ mutual exclusion โดยอัตโนมัติ

  • Process ที่ยังเข้าไม่ได้รออยู่ใน entry queue (แยกจาก waiting queue ของ condition variable)
  • เทียบกับ producer-consumer: ใช้ monitor แล้วเรื่อง mutual exclusion เป็นหน้าที่ของ monitor ไปเอง สิ่งที่ยังต้องมีคือเงื่อนไขอย่าง "buffer เต็มให้รอ" จึงใช้ condition variable แทน semaphore
  • condition x, y; มี operation ชื่อ wait/signal เหมือน semaphore: x.wait() = process เข้า monitor มาแล้วแต่ต้องรอเงื่อนไข x → ถูก suspend ลง waiting queue ของ x; x.signal() = resume process ที่เคย x.wait() (ถ้ามี)
  • จุดสำคัญ: process ที่ถูก signal ปลุก ไม่ได้ทำงานต่อทันที แต่กลับไปต่อคิวใน entry queue และการ signal เมื่อไม่มีใครรอ ไม่มีผลอะไรเสียหาย (อุปมา: นัดแม่ปลุกแต่ตื่นเองก่อน แม่มาปลุกซ้ำก็ไม่เสียหาย)

ทางแก้ Dining Philosophers ด้วย monitor dp (ไม่มีการถือตะเกียบข้างเดียวค้างไว้ จึงไม่เกิด deadlock):

monitor dp {
    enum {THINKING, HUNGRY, EATING} state[5];   /* สถานะของนักปราชญ์แต่ละคน */
    condition self[5];                          /* condition variable คนละ 1 ตัว */

    void pickup(int i) {              /* เรียกเมื่อหิว */
        state[i] = HUNGRY;
        test(i);
        if (state[i] != EATING)       /* เทสแล้วยังกินไม่ได้ */
            self[i].wait();           /* หลับรอใน waiting queue ของ self[i] */
    }
    void putdown(int i) {             /* เรียกเมื่อกินเสร็จ */
        state[i] = THINKING;
        test((i+4) % 5);              /* สะกิดเพื่อนบ้านซ้าย: ถ้าหิวและกินได้ให้ตื่น */
        test((i+1) % 5);              /* สะกิดเพื่อนบ้านขวา */
    }
    void test(int i) {                /* ฟังก์ชันหลัก: กินได้เมื่อครบ 3 เงื่อนไข */
        if (state[(i+4)%5] != EATING && state[i] == HUNGRY && state[(i+1)%5] != EATING) {
            state[i] = EATING;
            self[i].signal();         /* ปลุกตัวเอง (กรณีมาจาก wait ใน pickup) */
        }
    }
    void initialize() {
        for (int i = 0; i < 5; i++) state[i] = THINKING;
    }
}
/* ใช้งาน: dp.pickup(i) → EAT → dp.putdown(i) */
  • เรียก test จาก pickup: ตั้ง HUNGRY แล้วเทส ไม่ผ่านก็ wait ตัวเอง (self[i].signal() ท้าย test ในเคสนี้เป็นการเรียกเกินความจำเป็น ไม่เสียหาย)
  • เรียก test จาก putdown: กินเสร็จตั้ง THINKING แล้วสะกิดซ้าย-ขวา เพื่อนบ้านที่หิวและกินได้จะได้กินต่อ
  • ข้อสรุปของอาจารย์: วิธีนี้ ไม่เกิด deadlock (เท่ากับหันไปดูซ้าย-ขวาก่อนแล้วหยิบตะเกียบทั้ง 2 ข้างพร้อมกัน) แต่ ยังเกิด starvation ได้: หันซ้ายมีคนกิน รอจนซ้ายเสร็จ หันขวากินอยู่ สลับกันไปเรื่อย ๆ อดตายในที่สุด

Java Synchronization (คลิป 11.2)

Java มีหลักการเหมือน monitor ทุกอย่าง: entry set = entry queue, wait set = condition queue, notify = signal และ object ทุกตัวมี lock ติดตัวอยู่แล้ว

  • synchronized method: ณ เวลาหนึ่งมีเทรดเดียวทำงานกับ synchronized method ของ object นั้นได้ เทรดแรกที่เรียกเป็น owner (เจ้าของ lock) เทรดอื่นไม่ว่า method เดียวกันหรือตัวอื่นต้องไปรอใน entry set ล็อก/ปลดล็อกเป็นอัตโนมัติทั้งคู่ (เรียก = ล็อก, method จบ = ปลดล็อก) ใน class เดียวมี method สองแบบผสมกันได้ lock มีผลเฉพาะกลุ่ม synchronized
  • wait() ทำ 3 อย่าง: 1) release object lock ทันที (ไม่ต้องรอจบ method) 2) state = blocked 3) เข้าสู่ wait set
  • notify(): เลือก thread ใด ๆ จาก wait set ("อะไรก็ได้" เพราะ Java spec ไม่กำหนด ขึ้นกับ JVM) → ย้ายไป entry set → ตั้งเป็น Runnable ไปแข่ง lock ใหม่ ไม่ได้รันทันที
  • notifyAll(): ย้ายทุก thread จาก wait set เข้า entry set เป็นกลยุทธ์ conservative เหมาะเมื่อไม่ไว้ใจการเลือกของ JVM และมีหลาย thread ใน wait set (โปรแกรมเมอร์เลือกเองไม่ได้)
class BoundedBuffer {
    synchronized void insert(Object item) {   /* producer เรียก */
        if (count == size) wait();            /* เต็ม: ปล่อย lock แล้วเข้า wait set */
        /* ใส่ item, count++ */
        notify();                             /* ปลุก consumer ที่รออยู่ (ถ้าไม่มีก็ไม่เป็นไร) */
    }
    synchronized Object remove() {            /* consumer เรียก */
        if (count == 0) wait();               /* ว่าง: รอ producer */
        /* ดึง item, count-- */
        notify();
    }
}
ตัวอย่าง Counter พิสูจน์ความจำเป็นของ synchronized
  1. count เริ่ม 5, 2 เทรด (increment + decrement แบบแตก 3 สเต็ป + sleep สุ่ม) ทำงาน 1 ครั้ง ถ้าถูกต้องต้องได้ 5
  2. มี synchronized → ได้ 5 ถูกต้องทุกครั้ง
  3. ถอด synchronized ออก → ได้ 4, 5 หรือ 6 ขึ้นกับว่าเทรดไหนเสร็จทีหลัง อาจารย์เตือนว่าแบบนี้ถ้ามีปัญหาจะไล่ยากมาก เพราะบางทีถูกบางทีผิด
  • Java Semaphore class (มีตั้งแต่ Java 5 ก่อนหน้าต้องสร้างเองด้วย synchronized): acquire() = wait (รอจน value > 0 แล้ว value--), release() = signal (value++ + notify) ใช้ acquire/release ครอบช่วงอัปเดต count โดยสร้าง semaphore เริ่มค่า 1 ก็ได้ผลถูกต้อง
  • Synchronized block: ล็อกเฉพาะจุดสำคัญเพื่อเพิ่ม degree of concurrency เช่นส่วนสุ่มเลข/sleep ปล่อยให้เทรดทำพร้อมกันได้ แต่ครอบเฉพาะบล็อกอัปเดต count ด้วย synchronized (this) { count++; }
ข้อผิดพลาดที่พบบ่อย
  • อย่าใช้ yield() แทน wait(): yield แค่ยอมออกจาก CPU ไปต่อคิว ready queue แต่ ไม่ปลดล็อก object wait ปลดล็อกด้วย อุปมาอาจารย์: "ล็อกห้องไว้ แทนที่จะเปิดประตูออก กลับล็อกห้องค้างไว้แล้วปีนหน้าต่างออกไป"
  • notify เลือกเทรดแบบ "อะไรก็ได้" ตามแต่ละ JVM อย่าสมมติว่าปลุกตัวที่เราอยากให้ตื่น
มักออกสอบ
  • ไล่ interleaving count++/count-- หาค่าสุดท้าย (ตัวอย่าง S0-S5 ได้ 4) + นิยาม race condition
  • นิยาม critical section + 3 เงื่อนไข (mutual exclusion, progress, bounded waiting) พร้อมตัวอย่างที่ไม่ผ่านข้อ 2 และข้อ 3
  • Peterson: ตัวแปร turn + flag[2] + สมมติ LOAD/STORE atomic, Bakery: กดบัตรคิว (ticket, pid) ใช้ได้กับ n process
  • นิยาม wait/signal (P/V) atomic, counting vs binary semaphore (binary = mutex lock), การใช้ S = 1 คุม critical section
  • Implementation แบบไม่ busy waiting: block/wakeup, เงื่อนไข value < 0 กับ value <= 0, bounded waiting ขึ้นกับ wakeup (FIFO = ผ่าน)
  • ค่าเริ่มต้น semaphore ของ 3 classical problems: Bounded-buffer mutex=1, full=0, empty=N; Readers-Writers mutex=1, wrt=1, readcount=0; Dining chopstick[5] = 1 + โครงสร้างโค้ดและจุดที่ทำให้เกิด deadlock
  • Monitor: 1 process ต่อครั้ง, entry queue vs waiting queue ของ condition, signal แล้วกลับ entry queue, ทางแก้ DP ด้วย state[5] + self[5] + pickup/putdown/test (ไม่ deadlock แต่ starvation ได้)
  • Java: object ทุกตัวมี lock, wait() ทำ 3 อย่าง, notify() vs notifyAll(), entry set/wait set, wait กับ yield ต่างกันที่การปลดล็อก, Counter ถอด synchronized แล้วได้ 4/5/6, Java Semaphore (Java 5+) acquire/release
  • POSIX semaphore: sem_init(&mutex, 0, 1) ความหมายพารามิเตอร์, sem_wait/sem_post = P/V, compile ด้วย -lpthread, macOS ต้องใช้ named semaphore

Deadlock

แนวคิดพื้นฐาน (คลิป 11.3)

อุปมาของสไลด์และคลิป: จราจรทางเดียวบนสะพานแคบ แต่ละช่วงสะพาน = resource รถสองคันเจอกันกลางสะพานไม่มีใครยอมถอย ก็ไม่มีใครไปถึงจุดหมาย แปลงเป็น OS: รถ = process, ถนน = resource แก้ได้ถ้ามีรถถอย (preempt resources + rollback) อาจต้องถอยหลายคัน และถ้ากำหนดให้ฝั่งหนึ่งยอมถอยเสมอก็เกิด starvation ได้

  • Deadlock = process ตั้งแต่ 2 ตัวขึ้นไป รอกันไม่สิ้นสุด สำหรับ event ที่เกิดจาก process ที่กำลังรอเท่านั้น เมื่อเกิดแล้วมีโอกาสขยายตัว (อุปมา: เริ่มติดแค่ 4 แยกเดียว ถ้าไม่มีใครแก้ ขยายจนติดทั้งเมือง)
  • Starvation = indefinite blocking: process ไม่ถูกดึงออกจาก semaphore queue เลย ผลลัพธ์เหมือน deadlock (process ไม่จบ) แต่ starvation กระทบเฉพาะ process ไม่กี่ตัว ส่วน deadlock ขยายทั้งระบบได้ จึงสนใจแก้ deadlock มากกว่า
  • ข้อเท็จจริงสำคัญ: ส่วนใหญ่ OS ไม่ป้องกันและไม่จัดการ deadlock ระดับ user process เลย

ตัวอย่าง deadlock จาก semaphore (S, Q เป็น binary semaphore ค่าเริ่มต้น 1 ดูพื้นฐาน semaphore ที่ หัวข้อ Synchronization):

P0: wait(S);  wait(Q);  ...  signal(S);  signal(Q);
P1: wait(Q);  wait(S);  ...  signal(Q);  signal(S);
ไล่เหตุการณ์ที่อาจารย์ให้ trace
  1. OS ให้ P0 ทำก่อน: P0 wait(S) ถือ S
  2. OS สลับไป P1: P1 wait(Q) ถือ Q
  3. P0 ทำ wait(Q): Q ว่างแล้ว (P1 ถืออยู่) → P0 ไปรอใน wait state
  4. P1 ทำ wait(S): S ว่างแล้ว (P0 ถืออยู่) → P1 ไปรอใน wait state
  5. P0 รอให้ P1 signal(Q), P1 รอให้ P0 signal(S) ทั้งคู่ออกมาทำงานอีกไม่ได้เลย → deadlock

Deadlock Characterization: 4 เงื่อนไขจำเป็น (ต้องครบพร้อมกัน)

เกิด deadlock ได้ต้องมีทั้ง 4 เงื่อนไขพร้อมกัน ขาดข้อใดข้อหนึ่งก็ไม่เกิด อาจารย์ผูกทุกข้อกลับไปที่โค้ด S/Q ด้านบน:

  1. Mutual exclusion: ทรัพยากรให้ใช้ได้ครั้งละ 1 process (S, Q เป็น binary semaphore)
  2. Hold and wait: process ถือ resource อย่างน้อย 1 อันแล้วรอขอ resource ที่ถือโดย process อื่น (P0 ถือ S รอ Q, P1 ถือ Q รอ S)
  3. No preemption: resource ปล่อยได้เฉพาะโดยสมัครใจจากเจ้าของเมื่อทำงานเสร็จ (P0 คืน S ได้ต่อเมื่อเรียก signal(S) เอง ไม่มีใครดึงออกจากมือได้)
  4. Circular wait: มีชุด process รอวนกันเป็นวง P0 → P1 → P2 → ... → P0 (P0 รอ Q ของ P1, P1 รอ S ของ P0)

ตัดเงื่อนไขใดเงื่อนไขหนึ่งออก = แก้ deadlock ได้ แต่อาจารย์ย้ำว่า "พูดง่ายแต่ทำยาก"

Resource-Allocation Graph (RAG)

  • Vertex: วงกลม = P (process), สี่เหลี่ยม = R (resource type) จุดข้างในสี่เหลี่ยม = จำนวน instances ของ type นั้น (เช่น ปริ้นเตอร์ 4 ตัวใส่จุด 4 จุด)
  • Edge (มีทิศ): request edge Pi → Rj = Pi ขอ Rj, assignment edge Rj → Pi = Rj ถูกให้ Pi
กฎการอ่านกราฟ (ตัดสินจาก cycle)
  • กราฟ ไม่มี cycle → ไม่มี deadlock แน่นอน 100%
  • มี cycle + แต่ละ resource type มี instance เดียว → deadlock แน่นอน (ตัวอย่างคลิป: cycle P1 → R1 → P2 → R3 → P3 → R2 → P1 คือ deadlock ระหว่าง P1, P2, P3)
  • มี cycle + มี หลาย instance → สรุปได้แค่ "มีความเป็นไปได้" (possibility) (ตัวอย่างคลิป: cycle ระหว่าง P1 กับ P3 แต่ R1 มี 2 ชิ้น ถ้า P2 คืน R1 ปุ๊บ P1 ก็ใช้ได้ จึงไม่เกิด deadlock)

วิธีจัดการ Deadlock 3 ทาง

  1. ทำให้ระบบ ไม่เข้าสู่ deadlock เลย แบ่งเป็น prevention (ป้องกัน) กับ avoidance (หลีกเลี่ยง)
  2. ยอมให้เกิดแล้ว recover (detection + recovery)
  3. ไม่สนใจ แกล้งทำเป็นไม่มี deadlock ถ้าเกิดจริงก็เป็นหน้าที่คน/แอดมินจัดการเอง เช่น reboot, ใช้โดย OS ส่วนใหญ่ รวมถึง UNIX

Deadlock Prevention: ตัดเงื่อนไขทีละข้อ (คลิป 11.4)

  1. ตัด Mutual Exclusion: ทำไม่ได้กับทุกทรัพยากร ทรัพยากร sharable (อ่านพร้อมกันได้) ไม่ต้องมี แต่ nonsharable ธรรมชาติของมันต้องใช้ทีละตัว บังคับธรรมชาติมาไม่ได้
  2. ตัด Hold and Wait: รับประกันว่า process ที่ขอ resource ต้องไม่ถือ resource อื่น ให้ขอครบทุกอย่างก่อนเริ่ม หรือขอได้เมื่อไม่ถืออะไรเลย ตัวอย่างคลิป: P1 ต้องได้ disk + printer พร้อมกันจึงเริ่มทำงานได้ ปัญหา 2 อย่าง: ถ้าไม่เคยได้พร้อมกันเลย P1 ไม่ได้ทำงานเลย (starvation) และถ้าได้แล้วใช้ไม่ทับกันก็เปลือง เช่น P1 อ่าน disk 10,000 record ประมวลผล 15 นาที แต่ถือ printer ค้างไว้ตลอด → printer ว่างงานอย่างน้อย 15 นาที (utilization ต่ำ)
  3. ตัด No Preemption (ทำให้มี preemption): ถ้าขอแล้วไม่ได้ ต้องปล่อย resource ที่ถือทั้งหมด ใส่ไว้ในรายการรอ จะรันใหม่เมื่อได้ของเก่า + ของใหม่ครบ ปัญหา: จากเดิมรอตัวเดียวกลายเป็นรอทั้งตัวเก่าและตัวใหม่ มีโอกาส starvation
  4. ตัด Circular Wait: จัด total ordering ให้ resource type แล้วบังคับให้ขอตามลำดับ increasing order ตัวอย่างตัวเลขคลิป: กำหนด disk = 4, printer = 11 กฎคือ "ยังขอเลข 4 ไม่ได้ ห้ามถือเลข 11" ทำให้ P1 ที่ยังขอ disk (ถูก P2 ถือ) อยู่ ไม่มีวันได้ printer เส้น request ที่จะก่อวงไม่เกิดขึ้น ปัญหา: เลขมาจากสถิติการใช้งาน กระทบ process ที่ต้องใช้ printer ก่อน disk กฎนี้อาจไม่เหมาะกับ process บางกลุ่ม

สรุปคลิป: ไม่ว่าป้องกันข้อไหนก็มีปัญหาตามมาเสมอ (ประสิทธิภาพ/การใช้ทรัพยากรไม่คุ้ม) ทำได้ในทางทฤษฎีแต่ทางปฏิบัติไม่คุ้มเสีย OS จึงเลือกไม่ใช้ prevention

Deadlock Avoidance (คลิป 11.5)

  • ต้องมี a priori information: process ต้องแจ้ง OS ล่วงหน้าว่าจะใช้ทรัพยากรอะไร และ max ใช้กี่ตัว (โมเดลง่ายสุด) พอขอแต่ละครั้ง OS ตรวจทุกครั้งว่าถ้าให้ไประบบจะมีโอกาสเกิด deadlock ไหม แค่มีโอกาสก็ไม่ให้
  • Safe state = ระบบรู้ว่าไม่เกิด deadlock แน่นอน → ให้ได้; Unsafe state = มีความเป็นไปได้จะเกิด → avoidance คือไม่เข้า unsafe state เลย
  • กรณี instance เดียวต่อ type ใช้ resource-allocation graph + claim edge (เส้นประ): claim edge Pi - -> Rj หมายถึง Pi อาจขอ Rj ในอนาคต (สิ่งที่แจ้งไว้ล่วงหน้า) เมื่อขอจริงเปลี่ยนเป็น request edge เมื่อได้รับเป็น assignment edge เมื่อปล่อยกลับเป็น claim edge
  • วิธีตัดสิน: ลองเปลี่ยน claim → assignment ชั่วคราว ถ้ากราฟ ไม่เกิด cycle อนุมัติ, เกิด cycle ปฏิเสธ แล้วดึงด้านกลับเป็นเส้นประ ตัวอย่างคลิป: P2 ขอ R2 ทำให้เกิด cycle P1 → R2 → P2 → R1 → P1 ระบบจะ unsafe จึงไม่ให้ ทำแบบนี้ทุกครั้งที่มีการร้องขอ
  • เหตุผลที่ OS ไม่ทำ: ต้องเช็คหา cycle ทุกครั้งที่ขอ และการหา cycle ใช้ O(n^2) เมื่อ n คือจำนวนจุดยอด ระบบไม่มีประสิทธิภาพ + กระบวนการจริงไม่รู้ resource ที่จะใช้ล่วงหน้า (อาจารย์ว่าแนวคิดพอเข้ากับระบบ batch สมัยก่อน)
  • กรณีหลาย instance ต่อ type ใช้ Banker's Algorithm (ปัญหาเดียวกันคือการเช็ค safe state แต่ละครั้งใช้เวลานานมาก ยิ่ง process เยอะทรัพยากรเยอะยิ่งนาน)
อ่านเพิ่ม: Banker's Algorithm (สไลด์ No.07 มีตัวอย่างเต็ม)

หมายเหตุ: อาจารย์แจ้งในคลิปว่าไม่อยู่ในสโคป แต่มีในสไลด์ ควรอ่านเผื่อไว้

ใช้กับ n process, m resource type ข้อมูลที่ต้องมี: Available (เวกเตอร์ m), Max (n x m), Allocation (n x m) และ Need = Max - Allocation

Safety Algorithm: ตั้ง Work = Available, Finish[i] = false ทั้งหมด → หา i ที่ Finish[i] = false และ Need_i <= Work → Work += Allocation_i, Finish[i] = true → ถ้า Finish เป็นจริงทุกตัว = safe state

Resource-Request Algorithm (เมื่อ Pi ขอ Request): 1) Request <= Need? ถ้าไม่ใช่ = error เกิน claim 2) Request <= Available? ถ้าไม่ใช่ = ต้องรอ 3) จำลอง allocate: Available -= Request, Allocation_i += Request, Need_i -= Request → ถ้า state ที่ได้ safe ให้จริง ถ้า unsafe Pi ต้องรอและคืนสถานะเดิม

ตัวอย่างสไลด์: 5 process (P0-P4), resource A(10), B(5), C(7), Available = (3,3,2); Need: P0(7,4,3), P1(1,2,2), P2(6,0,0), P3(0,1,1), P4(4,3,1) → safe sequence <P1, P3, P4, P2, P0>

P1 ขอ (1,0,2) (ไม่เกิน Need และไม่เกิน Available (3,3,2)) → จำลองแล้ว safe sequence <P1, P3, P4, P0, P2> → อนุมัติ สไลด์ทิ้งคำถาม: P4 ขอ (3,3,0) ได้ไหม? P0 ขอ (0,2,0) ได้ไหม?

ข้อเสียของ Banker's: job ต้องแจ้ง max, จำนวน resource รวมต้องคงที่, จำนวน job ต้อง fix, overhead สูง, ใช้ resource คุ้มไม่ดี (สมมติ worst case) และ scheduling แย่ลง

Deadlock Detection (คลิป 11.6)

ยอมให้ระบบเข้า deadlock state + มี detection algorithm รันเป็นระยะ + recovery scheme

  • Instance เดียวต่อ type: ใช้ wait-for graph แปลงจาก RAG มาเป็นกราฟ process ต่อ process (Pi → Pj ถ้า Pi รอ resource ที่ Pj ถืออยู่) มี cycle = มี deadlock การหา cycle ใช้ O(n^2) ตัวอย่างคลิป: แปลงแล้วพบ cycle ที่เกี่ยวข้อง P1, P2, P3, P4 → deadlock ทั้ง 4 ตัว
  • หลาย instance: ใช้ Available, Allocation, Request (n x m) ทำ Detection Algorithm ทำนองเดียวกับ safety algorithm ถ้า Finish[i] = false บางตัว → ระบบ deadlock โดย Pi เหล่านั้นติด deadlock ความซับซ้อน O(m x n^2)
  • ปัญหาของ detection ที่ OS เลยไม่ทำ: ตรวจ บ่อยแค่ไหน? น้อยไปปัญหาเล็กขยายใหญ่แก้ยาก บ่อยไป OS เสียเวลาแทนที่จะให้บริการ user + ตัว detection เองก็ O(n^2)

ตัวอย่างสไลด์ (หลาย instance): 5 process, A(7), B(2), C(6) ตอนแรกได้ sequence <P0, P2, P3, P1, P4> Finish จริงหมด = ไม่ deadlock พอ P2 ขอ C เพิ่ม 1 → reclaim ของ P0 ได้แต่ไม่พอให้คนอื่น → deadlock มี P1, P2, P3, P4

Recovery from Deadlock (คลิป 11.6)

วิธี 1: Process termination

  • Abort deadlocked process ทั้งหมด: ง่ายสุดแต่อาจแย่ที่สุด ไม่มีใครเสร็จเลย และ user รันใหม่ก็อาจติด deadlock ซ้ำ
  • Abort ทีละตัวจนวงหัก: ดีกว่า แต่ถ้าไม่มีเกณฑ์เลือกที่ดีสุดท้ายก็อาจต้องจบทั้งหมด
  • เกณฑ์เลือก (ยกตัวอย่าง): priority (ต่ำกว่าถูกจบก่อน), ทำงานมานานไหม/เหลือเท่าไร (จบตัวเพิ่งเข้ามา เพราะยังใช้ทรัพยากรไม่มาก), ใช้ resource อะไรไปแล้ว/ต้องใช้อะไรอีก, ต้อง terminate กี่ process, interactive หรือ batch

วิธี 2: Resource preemption (ขอ resource คืนชั่วคราวแล้วให้ process ทำต่อภายหลัง)

  • Selecting a victim: เลือกว่าจะเอา resource จากใคร โดยลด cost
  • Rollback: คืน resource กลางคันอาจทำให้ข้อมูลไม่ถูกต้อง ตัวอย่างอาจารย์: process กำลังโอนเงิน ถอนจากต้นทางแล้วยังไม่ฝากปลายทาง ถ้าคืน resource เดี๋ยวนั้นเงินหาย → ต้อง rollback ไปจุด safe state (ก่อนถอน) แล้ว restart
  • Starvation: process เดิมอาจถูกเลือกเป็น victim ตลอด ทำงานไปได้ไม่นานก็โดนขอคืน วนไปเรื่อย ๆ → แก้โดยใส่จำนวน rollback เข้าไปใน cost factor
บทสรุปของทั้งชุด (จากคลิป)
  • ทุกแนวทาง (prevention, avoidance, detection+recovery) ทำได้ แต่ประสิทธิภาพและการใช้ทรัพยากรไม่คุ้ม
  • OS ส่วนใหญ่ (รวม UNIX) เลือกวิธี ignore: ไม่จัดการ deadlock ระดับ user process
  • ข้อสรุปของอาจารย์: นักเขียนโปรแกรมต้องป้องกัน deadlock เอง เพราะ OS ไม่มีกลไกช่วย
มักออกสอบ
  • นิยาม deadlock vs starvation (indefinite blocking) + ไล่ตัวอย่าง semaphore S/Q ว่าทำไมติดกันตาย
  • 4 เงื่อนไขจำเป็น (ออกบ่อยมาก): mutual exclusion, hold and wait, no preemption, circular wait + ข้อเท็จจริงว่าตัดข้อเดียว deadlock หาย
  • RAG: cycle กับ instance เดียว (deadlock แน่) กับหลาย instance (มีโอกาสเท่านั้น), ไม่มี cycle = ไม่ deadlock
  • OS ส่วนใหญ่ (UNIX) เลือกวิธีใด → ignore
  • Prevention: ตัดเงื่อนไขไหนด้วยวิธีใด + ปัญหาของแต่ละวิธี (printer ว่าง 15 นาที, starvation, กฎ disk=4/printer=11)
  • Avoidance: safe vs unsafe state, claim edge, ทำไม OS ไม่ทำ (O(n^2) ทุกครั้ง + ต้องแจ้งล่วงหน้า)
  • Banker's: Need = Max - Allocation, ไล่ safety algorithm หา safe sequence (ตัวอย่าง <P1, P3, P4, P2, P0>) อยู่ใน details ข้างบน ควรอ่านเผื่อแม้ไม่อยู่ในสโคป
  • Detection: wait-for graph O(n^2) (หลาย instance O(m x n^2)), ตัวอย่างสไลด์ P2 ขอ C เพิ่ม 1 → deadlock P1-P4
  • Recovery: เกณฑ์เลือก victim, rollback (ตัวอย่างโอนเงิน), starvation จากการโดนเลือกเป็น victim ตลอด
